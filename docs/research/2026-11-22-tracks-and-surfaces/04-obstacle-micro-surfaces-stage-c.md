## 1. Физическая мотивация и первичная трибология микро-покрытий

### 1.1. Почему макро-секции `SurfaceMap` не решают задачу препятствий

`SurfaceMap` (`native/src/terrain/surface.cpp:63-99`) представляет собой плоский массив непересекающихся полуоткрытых макро-интервалов `[start_m, end_m)` со строгими ограничениями:
1. Запрет перекрытий и требование вместимости переходных воротников `end_m - start_m >= 0.5 * (b_left + b_right)` (`surface.cpp:85-97`).
2. **Рассинхронизация с процедурной геометрией:** центры корней в `Roots::bump_centres_m()` (`native/src/terrain/obstacles.cpp:84-96`) и узлы `RockGarden::nodes()` (`obstacles.cpp:13-57`) порождаются ГПСЧ по `seed` и `jitter`. На реальном лесном подъёме `hardpack` ($\mu_{\text{peak}} = 0.80$) сами корни шириной `25–28 см` имеют скользкую древесину/кору ($\mu \approx 0.20\text{–}0.45$), а 40-сантиметровые промежутки между ними остаются плотным грунтом ($\mu = 0.80$). Выразить это вручную в `surface_sections` невозможно без дублирования ГПСЧ и поломки `track_sha256` при любом изменении параметров препятствия.

### 1.2. Данные первичной трибологии для протекторной резины (~50–65 Shore A)

## 2. Пространственная привязка микро-покрытий к `Obstacle`

### Сравнение архитектурных вариантов

1. **Вариант C1 (рекомендуемый) — опциональные поля `surface` и `surface_blend_m` на самом препятствии с генерацией точных локальных спанов при компиляции трассы:**
   - В описание препятствия в TOML добавляются опциональные ключи `surface = "wet_wood"` и `surface_blend_m = 0.02` (эмитятся при сериализации только если заданы $\implies$ **`track_sha256` всех существующих трасс остаётся побайтово неизменным**, как для `blend_m == 0.0` на Этапе А).
   - На этапе подготовки (`prepare` / построение `SurfaceResolver`, вне `BIKE_NONBLOCKING` горячего цикла!) каждое препятствие с заданным `surface` порождает детерминированный отсортированный массив микро-спанов `MicroSpan{start_m, end_m, blend_m, spec}`:
     - **`Roots`:** отдельный спан `[start_m + c - width_m/2, start_m + c + width_m/2]` для каждого корня $c \in \text{bump\_centres\_m}()$ — **грунтовые промежутки между корнями сохраняют фоновый `SurfaceMap`!**
     - **`Pothole` / `SlopedPothole` / `BowlPothole` / `GOut`:** центральная донная зона (например, где $z_{\text{obs}}(x) \le -0.5\,d$), моделирующая лужу или грязевую линзу `mud_lens` на дне впадины.
     - **`RockGarden`:** спаны вокруг положительных каменных выступов ($z_{\text{obs}}(x) > 0$), оставляющие грунтовые карманы между камнями базовому покрытию.
     - **`SquareEdge` / `Drop` / `Kicker` / `TrapezoidBump`:** весь интервал `[start_m, end_m)`.
2. **Вариант C2 — ручная разметка отдельной картой `micro_sections` в TOML:** отвергается, так как нарушает единый источник истины с `seed`-зависимыми координатами корней и камней.

### Правило композиции и `BIKE_NONBLOCKING`

- **Критическое требование RTSan:** методы `Roots::bump_centres_m()` (`obstacles.cpp:84-96`) и `RockGarden::nodes()` (`obstacles.cpp:97`) сейчас аллоцируют `std::vector<double>` при каждом вызове. Поэтому вычислять их внутри шага физики запрещено: плоский отсортированный массив `std::vector<MicroSpan>` строится **один раз в конструкторе** `SurfaceResolver`, после чего `eval_surface(x)` и `uniform_surface_for_span(x_min, x_max)` выполняют бинарный поиск (`std::ranges::upper_bound`) за $O(\log M)$ с **нулём аллокаций**.
- Внутри микро-спана действует правило перекрытия (overlay): микро-покрытие замещает подстилающий `SurfaceSample` из `SurfaceMap`, а на краях `[s - b/2, s + b/2]` и `[e - b/2, e + b/2]` ($b = \text{surface\_blend\_m}$, типично `0.01–0.03 м`, валидация $b \le \text{span\_len}$) смешивается с подстилающим `eval_surface(base_map, x)` тем же полиномом Эрмита $t^2(3-2t)$.

## 3. Суб-патчевая физика контакта, баланс энергии и `SurfaceLabel`

### 3.1. Пятно контакта одновременно на грунте и мокром корне (`hardpack` $\mu=0.80 \to$ `wet_wood` $\mu=0.25$)

- В **`DistributedTireWriter`** (`distributed_tire.cpp:759-800`) расчёт уже полностью по-станционный: станции на грунте несут $\mu = 0.80$, станции на корне — $\mu = 0.25$. За счёт хранения $\tilde{\xi} = \xi_{\text{phys}}\sqrt{r_k}$ (`строки 789–800`) проезд станции через 2-сантиметровый воротник `hardpack -> wet_wood` **строго сохраняет упругую энергию сдвига** `stored_energy(d) == elastic_energy_j()`.
- В **`PneumaticTyreModel::evaluate_impl`** (`native/src/pneumatic/model.cpp:628-670`):
  - как только `uniform_surface_for_span` учтёт `MicroSpan`, любое пятно на границе корня автоматически переключится на гетерогенную ветку;
  - в режиме **`detailed`** (`DiscretisedBrush::step_heterogeneous`, `model.cpp:704-709`) каждая щетинка обрезается локальным пределом $\pm \mu_i f_i$, точно воспроизводя ранний срыв лучей на мокром корне при удержании лучей, ещё стоящих на грунте;
  - в режиме **`fast`** (`lumped_brush`, `model.cpp:653-663, 728-731`) вычисляется средневзвешенный по нормальным силам лучей `SurfaceSpec`. Когда вершина корня перехватывает 70–85 % нормальной нагрузки пятна, взвешенный $\bar{\mu}$ быстро падает с `0.80` почти до `0.25`, давая физически правильный срыв колеса при накате на корень без удорожания шага `1.25 мс`.

### 3.2. Совместимость с закрытым `rider::SurfaceLabel` (`native/src/rider/senses.hpp:21`)

- Микро-покрытия шириной `10–30 см` являются локальными свойствами препятствий, а не фоновым типом дороги.
- Расширять закрытый `enum class SurfaceLabel` (`asphalt, hardpack, loose, wet, scree`) на Этапе В **не требуется**: `TireDiagnostics::surface` имеет тип `std::string` (`tire_common.hpp:70`) и может публиковать `"wet_wood"` в телеметрию, тогда как `RiderSenses` читает макро-карту покрытий трассы (либо на Этапе Г использует таблицу приведения `wet_wood, wet_rock, mud_lens -> SurfaceLabel::wet`, `dry_wood, polished_rock -> SurfaceLabel::hardpack`).
