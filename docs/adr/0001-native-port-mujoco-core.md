# ADR 0001: C++-порт tick-path на MuJoCo — нативное ядро с двумя фронтендами

Статус: принято
Дата: 2026-10-04 (по дереву работы `.scratch/cpp-port/`)
Драйвер решения: **скорость симуляции**. Стоимость, трудоёмкость, план миграции — вне оценки (явное ограничение заказчика).

## Контекст

`bike-sim` — MuJoCo-симуляция (подвеска + всадник, физический шаг 0.5 мс). Потребители: живой viewer (нужен real-time или быстрее) и batch research (throughput). Текущий измеренный шаг ~1.8 мс (RTF ≈ 0.28 — медленнее реального времени); параллельный P-план оптимизации Python целится в ≤0.5 мс (RTF ≈ 1).

Вопрос: переписать ли проект на C/C++, в какой форме и на каком движке. Источник фактов — карта `.scratch/cpp-port/` (семь закрытых билетов; там же ссылки на профили и прототипы).

## Скорость: измеренные факты

| Источник | Факт |
|---|---|
| Анатомия шага (профиль HEAD) | Шаг ~1.8 мс; `mj_step` ~40 мкс (~2%); весь движок ~10%; Python-клей ~85–90% (телеметрия ~55%, force-writers ~30%); ~6460 вызовов и ~100 pybind-кроссингов на шаг |
| Microbench M4 (тот же `libmujoco.3.12.0`, та же модель nv=26) | `mj_step` ~32 мкс одинаково в C++ и Python; нативный клей почти бесплатен (heavy ≈ glue ~93 мкс); в нативном шаге движок — ~65% |
| Экстраполяция порта | Полный нативный шаг ≈ **200–400 мкс → RTF ~1.3–2.5×**; совпадает с аналитическим потолком 2–3.5× |
| Движок | Ни одна библиотека не покрывает нужную интроспекцию (named equality multipliers, mutable tendon bounds, re-entrant `mj_forward`, семантика `efc_*`). Ниже ~50 мкс движка — только собственный nv=26 constraint-слой |

## Ledger по формам

| | **stay** (post-P) | **гибрид** (extension) | **полный** (ext + CLI) | **bespoke** (полный + свой движок) |
|---|---|---|---|---|
| Шаг / RTF | ~500 мкс / ~1× | 200–400 мкс / ~1.3–2.5× | 200–400 мкс / ~1.3–2.5× | ~100–200 мкс? / ~2.5–5× (не измерено) |
| Batch-параллелизм | только процессы | нативные потоки | нативные потоки | нативные потоки |
| Планка корректности | сам оракул | полная (3 слоя) | полная (3 слоя) | **ослабленная** — только метрики/инварианты |
| **Плюсы** | нулевой риск; быстрая итерация; весь scipy-стек | снимает ~85–90% шага; вся инфраструктура Python жива; детерминированно проверяемо | + batch без интерпретатора; throughput × потоки; один core — оба потребителя | единственный путь ниже движковых ~50 мкс; полный контроль |
| **Минусы** | структурный потолок ~1× (интерпретатор не оптимизируется); viewer без запаса; batch зажат | шов + бремя верификации; Python-рантайм остаётся | viewer через replica-`mjData`; MJCF-билдер навсегда Python | теряется детерминированная траекторная проверка; свой contact/constraint solver; теряется MJCF-пайплайн; никакая библиотека это не покупает |

Замечание: «гибрид» и «полный» — один артефакт (нативный core), различаются только драйвером. Выбор «extension-only» был отвергнут: он теряет standalone-batch и потоковый throughput почти бесплатно-получаемые поверх того же ядра.

## Решение

**Go: нативное ядро C++23 поверх MuJoCo, два фронтенда — nanobind-extension и standalone CLI.**

1. **Граница — по такту.** Весь per-step/per-tick путь в native: цикл шагов, писатели сил (шины, мотор, ридер), контроллерный тик, телеметрия/рекордер (полный контракт каналов), intent-программы. Setup и эпизод-оркестрация остаются в Python: MJCF-билдер, terrain-gen, визуализация, CLI-инфраструктура, исследования, тесты-оракулы.
2. **Артефакт.** Одна нативная библиотека (**C++23**, CMake, clang, macOS arm64; проверено на Apple clang 21 / Xcode 26 — `std::expected`, `std::print`, ranges работают; C++26 частичен — не целимся). C++17 — лишь пол по nanobind, не потолок. Оговорка: libc++-фичи ≥C++20 гейтятся deployment-target'ом — при нужде собирать под старый macOS часть библиотеки отвалится. Фронт 1: nanobind-extension — живой viewer/интерактив и побитовая проверка шва из Python-тестов. Фронт 2: standalone CLI (fmt/CLI11) — headless batch со своими потоками (без GIL).
3. **Шов.** Кроссинги на границе intent-тика (10 мс → ~100–200 пересечений/с): команды в нативный цикл через очередь, состояние наружу — zero-copy views + каналы записей через очередь.
4. **Владение.** `mjModel`/`mjData` и все нативные буферы — собственность ядра. Python держит только views и очереди. Viewer рендерит локальный replica-`mjData` (snapshot по кадру; ~60 копий/кадр на nv=26 — измерено как тривиально).
5. **Стек замен** (arm64): Eigen (numpy), ProxQP + HiGHS (QP; Clarabel — опцион для SOC-круга хвата), write-only CSV + существующий Python-viz (implot — для живых кривых в native viewer), fmt/CLI11. MuJoCo и GLFW — те же нативные библиотеки. Единственный пробел — негладкое равенство активации (по дефолту выключено).
6. **Планка корректности** (фиксирована до порта): слой 1 — per-call идентичность ~1e-12; слой 2 — детерминированная эквивалентность эпизода (все каналы + тот же первый нарушающий шаг) до измеренного горизонта расхождения; слой 3 — статистическая эквивалентность метрик дальше. Python — оракул через golden-артефакты (сырой state + все каналы), не через live side-by-side.
7. **Bespoke — припаркованная опция с триггером:** собственный движок (Pinocchio + свой constraint/contact слой) рассматривается отдельным решением, если и только если измеренный RTF после порта недостаточен **и** движок остаётся доминирующей долей шага. Его ослабленная планка корректности — осознанная и зафиксированная цена.

### Численный контракт P2

Per-state writer gate сравнивает сырые байты результатов, включая знак нуля.
Для скалярных Python-выражений native собирается с `-ffp-contract=off`:
неявная FMA меняет число округлений и нарушает побитовое совпадение.
Явные `std::fma` остаются только там, где они воспроизводят numpy-операцию.

Побитовая эквивалентность привязана к той же платформе и численным библиотекам:
той же MuJoCo dylib, системной libm (включая `pow` через shim, запрещающий
замену `pow(x, 2)` на `x*x`) и Apple Accelerate CBLAS, к которой привязан numpy
этого окружения (`dot`, `@`, быстрый путь `norm`). Другая libm, платформа или
BLAS (например OpenBLAS) требует повторного per-state gate; переносимость
побитовых результатов между ними не предполагается.

## Безопасность native-ядра (hardening)

Unsafe-поверхность у выбранной архитектуры **тонкая и конкретная**: FFI-шов проходит на intent-тике (~100–200 кроссингов/с, не на шаге), а внутри ядра опасность — это работа по буферам `mjData` (`qpos`, `efc_*`, qfrc-ареи). Дисциплина: ядро — чистые функции над `std::span` поверх буферов, ноль аллокаций и ноль хранимых указателей на tick-path; валидация размеров (`nv`/`nefc`) один раз на входе; исключения не покидают FFI-границу (`noexcept` ядро + коды/`std::expected` на краю); при `gil_scoped_release` в секции не трогаем Python-объекты.

Проверенный на этом toolchain (Apple clang 21, SDK 26.5) набор флагов:

```
-Wall -Wextra -Wpedantic -Werror -Wconversion -Wsign-conversion -Wdouble-promotion
-Wshadow -Wcast-qual -Wformat=2 -Wundef -Wimplicit-fallthrough -Wnon-virtual-dtor
-Wold-style-cast -Woverloaded-virtual -Wnull-dereference -Wunsafe-buffer-usage
-ffp-contract=off                                  # сохраняет порядок округлений Python
-D_LIBCPP_HARDENING_MODE=_LIBCPP_HARDENING_MODE_FAST    # проверки границ libc++, ~суб-процент оверхеда
-fstack-protector-strong -ftrivial-auto-var-init=zero -mbranch-protection=standard -fvisibility=hidden
```

Отличия от заимствованного чеклиста (проверено): `-fstack-clash-protection` на clang **не поддержан для Darwin-таргета** (unused-argument, с `-Werror` ломает сборку) — исключён; `-D_FORTIFY_SOURCE=3` принимается, но на Darwin — почти no-op, оставлен без веса. MISRA C++:2023 таргетирует C++17 — при C++23 остаёмся на Core Guidelines как чеклисте. Safety Profiles (P3081) в шипящихся компиляторах нет — дисциплина + tooling, не компилятор.

**Toolchain-альтернативы (проверено установкой):** brew `llvm` 23.1.2 — тот же набор флагов, тот же `-fstack-clash-protection` отсутствует на Darwin; brew `gcc` 16.2.0 — единственный с рабочим `-fstack-clash-protection` на arm64, плюс уникальные ворнинги (`-Wlogical-op`, `-Wduplicated-cond`, `-Wuseless-cast`, `-Wstringop-overflow=4`); ASan в GCC работает (проверено), но `-fhardened` недоступен на Darwin-таргете, stdlib — libstdc++ (`_GLIBCXX_ASSERTIONS` вместо libc++-режимов), нужен `-isysroot` на 26.5 SDK (brew-линкер не жуёт `arm64e.x1` из SDK 27). **Вывод: primary — clang** (у GCC нет `-Wunsafe-buffer-usage` — самого ценного ворнинга под нашу поверхность `mjData`-буферов; stack-clash — защита от ROP, для локального численного ядра без сетевого входа не в модели угроз); GCC — вторым компилятором в CI ради уникальных ворнингов.

Multi-compiler hygiene: каждый TU ядра проходит compile-only sweep (`-fsyntax-only`) под обоими фронтендами с warnings-as-errors — clang набор + GCC набор (проверено: union реально шире, GCC ловит то, что clang пропускает — напр. `-Wcomment`). Чужие хедеры только через `-isystem`. Ложные срабатывания давятся точечным `#pragma GCC diagnostic` + комментарий, не глобальным `-Wno-*`.

Дежурный контур: тот же TU с `-fsanitize=address,undefined` в тестах (для extension — ASan через `DYLD_INSERT_LIBRARIES`, `detect_leaks=0`); `clang-tidy` (`cppcoreguidelines-*`, `bugprone-*`, `cert-*`) как errors; TSan при появлении потоков; дифференциальный тест C++-ядро vs Python-оракул на случайных `mjData`-состояниях — главный safety-net, он же слой-1 планки корректности.

## Последствия

- Честный масштаб выигрыша: против пост-P потолка ~1.3–2.5× на шаге — не порядок. Реальные выигрыши: запас под real-time (viewer на 0.5 мс с headroom), потоковый batch-throughput, детерминизм тик-пути.
- Поддерживаются две языковые базы; верификация порта — постоянная инфраструктура (golden episodes, perturbation-тест), а не разовая проверка.
- MJCF-билдер остаётся Python навсегда: модель компилируется один раз, вне горячего пути — это не уступка, а граница.
- Если пост-порт измерения покажут, что движок — остаточный доминант (~65% сейчас) и RTF не хватает, bespoke выходит из парковки как следующий отдельный ADR.
