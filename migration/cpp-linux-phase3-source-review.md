# Фаза 3 C++/Linux: изменения исходников и повторная проверка отчёта

Дата: 2026-10-21.

## Результат и границы

Из предоставленного Repomix восстановлены исходники и внесена часть реализации
фазы 3 из `docs/superpowers/plans/2026-10-20-cpp-linux-completion.md`.
**Фаза 3 целиком не выполнена и не закрыта.** Помимо обязательных запусков и
двухплатформенных эталонов остаются неперенесённые группы тестов и конкретные
пробелы в validation. Это передача внесённых изменений с картой оставшейся работы,
а не подтверждение готовности перехода к фазе 4.

Соблюдён запрет пользователя на компиляцию и запуск проекта: не выполнялись
компилятор, `-fsyntax-only`, линковка, CMake configure, pytest/CTest, приложения,
симуляции, бенчмарки, Docker, sanitizer/coverage/package-команды или проектные
скрипты. Проверки ниже — чтение исходников, AST/JSON как данных, сверка путей,
сравнение файлов и проверка/упаковка патча. Они не доказывают компилируемость,
линковку, численную эквивалентность или работоспособность.

Точный статус каждой задачи фазы находится в
`migration/cpp-linux-phase3-source-status.json`; соответствия тестовых функций —
в `migration/test-port-map.json`. Значения `port`, `golden`, `drop` описывают
решение по исходному тесту, **не результат его исполнения**. `planned` оставлен
там, где перенос или обоснованное решение ещё отсутствуют. Собранные pytest node
IDs не подставлялись из догадок. Python, binding graph и исследовательские данные
не удалялись; статусы квалификации и исторические измерения не повышались.

Из 53 задач фазы исходная реализация подготовлена для 13, частично внесена для
11, ещё 23 партии исходников не реализованы. Шесть задач исторических failures
требуют воспроизведения для диагноза. Ни одна из 53 задач не помечена полностью
закрытой: исходная реализация и выполнение её ворот — разные состояния.

Итог карты тестовых функций: **183 `port`, 58 `golden`, 35 `drop`, 2105 `planned`**.
Здесь `drop` означает обоснованное будущее удаление проверки вместе с Python,
а не удалённый файл. Параметризованные подслучаи со своим решением перечислены
в отчётах партий; количество функций не выдаётся за число pytest-сценариев.

## Что уже изменено

### Захват эталонов и тестовая инфраструктура: 3.01–3.03

Добавлены `tests/reference/_golden.py`, подключение к `_bits.py` и исходники тестов
самого capture hook. Захват включается явно через `BIKE_GOLDEN_CAPTURE`, записывает
ожидаемую сторону исходного сравнения и сохраняет для pytest-узла одну пару
JSON-массив/бинарный payload. Каждая запись содержит индекс, исходный node ID,
label, вид сравнения, dtype, shape, смещение, размер и исходные допуски для `close`.
Скаляр сохраняет `shape=[]`; превращение его в массив `[1]` не допускается.

В `native/tests/support/golden.{hpp,cpp}` добавлен последовательный C++ reader:
проверяются принадлежность sidecar узлу, непрерывность индексов и смещений,
размеры, dtype, label, ожидаемая форма, нехватка/лишние байты и полное потребление
записей через `done()`. Численные тесты используют явные формы для скаляров,
векторов и матриц. Для битового сравнения сравниваются бинарные представления,
включая signed zero и NaN; `close` использует записанные допуски. Отсутствующие
эталоны приводят к отказу теста, а не к пропуску или автоматическому обновлению.

Добавлен `native/tests/reference/CMakeLists.txt` с единым helper регистрации и
разделением обычных тестов и тестов, которым нужен engine/startup policy.
Скомпилированные пути передаются через приватные generated headers, чтобы
кавычки в compile definitions не ломали JSON-контекст проверок. При
`BUILD_TESTING=OFF` эта тестовая графа не создаётся.

Для episode добавлены native NPZ writer, сохранение/чтение, сравнение и команды
`bike-recording golden freeze|compare`. Capture использует полный `RideControl`
и физическую границу до/после `apply_forces`; выходной `qfrc_applied` берётся из
живого engine state, независимо от суммы компонентов. Ненумерические/list
каналы сохраняются отдельно от плоского представления для сравнения. Поддержка
старых форматов не синтезирует отсутствующие выходные силы из компонентов.

В `tests/fixtures/golden/episode/pinned_savage_40/` находятся только исходные
входы и рецепт будущего Python-захвата. Файлы с якобы измеренными эталонами
Darwin/Linux не создавались. Перенос исходных episode-regressions описан по
функциям в `migration/cpp-linux-phase3-episode-ports.md`: все девять функций,
десять случаев с учётом v1/v2. Проверка live total действительно меняет
ограниченный force buffer после `apply_forces`, затем сравнивает все наблюдения
и save/load; синтетического NPZ недостаточно для этой гарантии. Эти инварианты
не заменяют отдельный двухплатформенный Python oracle gate.

### Realtime: 3.04 и часть 3.34/3.36

Добавлены `bike-measure-realtime`, библиотека измерения и отчётов, native driver,
разбор аргументов и provenance. Измеряется весь цикл с boundary-вызовами и
финальным flush; setup и export учитываются отдельно. Задержка одного chunk
не переименовывается в задержку одного физического шага. При ошибке сохраняются
данные о завершённом префиксе и закрывается владелец runtime.

Повторения имеют отдельные fresh owners. Порог native-производительности не
превращается в положительный результат без warmup, трёх подходящих валидных
повторений и совместимых параметров/identity. Отсутствующие поля старого отчёта
остаются отсутствующими/null. Флаги физической валидности и realtime не заменяют
друг друга. Benchmark-вариант меняет политику остановки monitor; физические
параметры остаются теми же.

Исходники регрессий сохраняют все семь функций `test_realtime_measurement.py`,
шесть `test_measure_realtime_report.py` и 16 `test_performance_evidence.py`.
Добавлены отдельные проверки CLI, output-directory admission и управляемого
лимита wall clock. При повторном чтении Python-драйвера исправлены нормализация
причины crash, общий лимит 300 секунд и CSV-заголовок retention-off режима.
Ни один из этих сценариев в этой сессии не выполнялся; RTF не измерен.

### Validation: 3.37–3.40

Добавлены `bike_validation`, реестр операций, `bike-validate` и исходник
`migration_T54`. Реестр включает исходные benchmark cases; стенды используют
реальные native model/setup/runtime/recording владельцы и исходные горизонты и
пороги. Для calibration, holdout, valid-prefix, release и отчётов сохранено
разделение физической валидности, численной валидности, parity и performance;
пустой набор доказательств не становится положительным release verdict.

Полная таблица **30 фактических модулей** — в
`migration/cpp-linux-phase3-validation-review.md`. Заголовок исходного плана
ошибочно обещал 32, тогда как его собственные перечисления содержат 28 validation
и два physics файла; это исправлено.

**Эта часть остаётся частичной и по исходникам.** Среди явных ограничений:
изолированные parallel workers, некоторые custom-material/coercion/shape входы,
точное сохранение `shock_total`, полнота dependency identity и различие наблюдения
старого `sim.physical.sample` после каждого шага и новых завершённых immutable
intervals. Последнее меняет наблюдаемую последовательность и интегральные метрики;
его нельзя объявить буквальным переносом Python-драйверов до согласования
семантики и сравнения реальных результатов. Полный список приведён в отчёте
validation. Реестр CLI отвергает неприменимые выбранному модулю параметры и
повторы алиасов одного поля. Goldens всех публичных выходов ещё не захвачены.

Повторная сверка устранила конкретный сдвиг хода вилки: road/refinement берут
его из committed endpoint после каждого шага, сохраняя исходный порядок
`*1000 /1000`. Проверка покрытия требует непрерывных interval IDs и полного
опубликованного хвоста; стенды с фиксированной длительностью отвергают досрочный
исход. Диагностический replay сохраняет отчёт по префиксу. Эти изменения пока
подтверждены только чтением исходников и наличием регрессионного кода.

### Инструменты: 3.41–3.45

Добавлены корневые CMake presets, чистые и отрицательные sanitizer/RTSan controls,
coverage workflow, CPack binary/source recipes, package checks, общий безопасный
offline extractor, CI на presets и release checklist.

В source package используются конкретные архивы с проверкой их locked hashes;
шаг offline rehearsal теперь содержит воспроизводимую распаковку. Package audit
получает явную policy: отсутствие policy внутри install tree не должно превращать
проверку в пустую. Coverage не публикует пустой профиль как успешный результат.
Обычная тестовая выборка явно исключает `slow|audit|package`; сами labels ничего
автоматически не исключают.

Подробности решений и требуемых проверок — в
`migration/cpp-linux-phase3-tooling-review.md`. Начальная native project version
`0.0.0` соответствует задаче 3.44; это не выпуск релиза и не изменение Python
package version. Ни один CI lane, package smoke, sanitizer control или offline
rebuild здесь не запускался.

## Исправления самого плана

Согласованы JSON sidecar-массивы вместо несуществующих каталогов `NNN.json`,
порядок обязательного documentation audit в фазе 4, default OD-1, конкретная
offline распаковка и явное исключение audit/package из обычного CTest. Исправлены
пример scalar capture, helper регистрации, квалификация имён методов классов и
число validation-модулей.

Уточнён per-function подход к удаляемым Python-инструментам. Три native loader
контракта нельзя удалять вместе с extension loader. Аналогично
`tests/portability/test_numerics_discovery.py` содержит прямые действующие
`BikeNumerics.cmake` guards: record-only/no-Python mode, provider paths/bytes,
platform/ABI/symbol checks. Их нельзя считать покрытыми общей ссылкой на presets
или удалить по имени файла; оставшиеся строки карты сохраняют `planned`.

## Как применять передачу

Патч предназначен для настоящего checkout, соответствующего предоставленному
снимку. Текстовый архив содержит восстановленные файлы и изменения; исходные
бинарные файлы, Git ancestry и архивы зависимостей Repomix не включал. Поэтому
этот архив не объявляется самостоятельным воспроизводимым checkout.

При подготовке patch/export текстовые окончания нормализуются в LF и добавляется
конечный LF там, где Repomix его убрал. Существующие executable modes не меняются
патчем; новые shell entry points получают executable mode. Исходные разрешения
прочих файлов по Repomix не восстанавливаются достоверно. Для рабочего checkout
предпочтителен патч: он сохраняет имеющиеся бинарные данные и Git-историю.

Сводка фактической проверки файлов и SHA-256 переданных изменённых файлов
находится в export manifest. Успешная проверка применимости патча к нормализованной
текстовой базе означает только целостность передачи изменений, а не успешную
сборку или тест проекта.
