# Spatial 3D Native — необязательное исследование GPU Implementation Plan

> **Для исполнителей:** использовать superpowers:subagent-driven-development (рекомендуется) или superpowers:executing-plans для последовательного выполнения задач; отмечать шаги через `- [ ]`. Это необязательное исследование: его незавершённость не блокирует S54 и не разрешает менять физический CPU-контракт.

**Goal:** В ограниченном объёме установить, оправдана ли отдельная GPU-работа после измерения нативной пространственной реализации.

**Architecture:** CPU-симулятор остаётся источником истины. Раздельно оцениваются перенос части одного шага, пакетные симуляции и автономные генерация/анализ. Эксперименты не входят в шаг или граф зависимостей продукта; положительный результат требует отдельного архитектурного решения и плана квалификации.

**Tech Stack:** существующие C++-измерения и CPU-fixtures; платформенный GPU SDK только внутри необязательного эксперимента. Обязательная зависимость от Python/JAX/MLX не появляется в продукте, сборке, тестах или подготовке отчёта.

**Spec:** `../specs/2026-10-22-spatial-3d-native-design.md`, `2026-10-22-spatial-3d-native-master.md`, `2026-10-22-spatial-3d-native-contracts.md`, измеренная нагрузка S50 и решение о CPU S51/S52. Исторический P8 сохраняется как источник вопросов; его предположения и номер ADR не копируются.

## Общие ограничения

- Сейчас ничего не запускать и не компилировать: создаётся план, не прототип. Будущие числа получают статус только после реального измерения.
- S55 необязательна. Изучение исходников и документации может начаться раньше S50, но решение об ускорении требует конкретной квалифицированной CPU-базы.
- В рамках записки не менять dependency lock, backend по умолчанию, dt, закон шины, точность или принятые fixtures.
- Не создавать `docs/adr/0003-gpu-offload.md`: ADR0003 уже занят переходом к native-authoritative состоянию и удалением Python. Выбрать следующий свободный номер в фактическом checkout.
- Эксперимент только на Metal не доказывает переносимость на Linux; Linux backend/profile рассматривается отдельно, без обещания доступности CUDA.
- Точность GPU-результата, детерминизм, затраты передачи/подготовки и скорость полного заезда рассматриваются раздельно.
- Предположение `CPU8≈CPU1/6` или `100ns/ray` не представляется измеренной исходной скоростью.

## Исправления старого P8

Старый P8 начинался с «day1», хотя размеры tyre/grid и CPU-время ещё не были установлены, предлагал NumPy/MLX/Python и занимал уже используемый ADR0003. Новый порядок: измерить фактический однопоточный путь, при необходимости параллельный CPU-вариант, затем оценить объём работы для переноса. Изучение документации объясняет предполагаемые затраты, но не подтверждает ускорение.

В историческом H1 предлагался отказ при `GPU≥0.5*CPU`, что неоднозначно трактовало равенство относительно цели «2× быстрее». Здесь критерий точен: `gpu_end_to_end_s<=cpu_best_qualified_s/2`. Если точность, детерминизм или обязательное поведение не подтверждены, одна скорость не даёт положительного решения.

Необходимо учитывать dispatch, синхронизацию и передачу данных, нужных следующему последовательному шагу MuJoCo. Локальный shader benchmark без readback не отвечает на вопрос о полном tick. Перенос тысяч независимых эпизодов — другой режим продукта; он не ускоряет интерактивную поездку автоматически.

## S55 — Ограниченная исследовательская записка о GPU

**Dependencies:** измеренная CPU-нагрузка S50 и документированный результат S51/S52 для выбора лучшего квалифицированного CPU-варианта; при `not_selected` это измеренный однопоточный вариант. S54 не зависит от S55. До появления данных допустим только статус `desk-review/pending-measurement`.

**Files:** Create `docs/superpowers/audits/2026-10-22-spatial-3d-gpu-feasibility.md`, `tools/spatial_gpu/README.md`; при будущем измерении Create изолированные `tools/spatial_gpu/decision.hpp`, `tools/spatial_gpu/decision_test.cpp` и отдельный каталог прототипа выбранного API. Production `native/` и корневой CMake продукта здесь не меняются.

**Consumes:** фактическая нагрузка grid/ray/material, время CPU с одним потоком и пулом, контракты точности/состояния/владения и доступность оборудования. **Produces:** записка с независимыми решениями H1/H2/H3: `go-for-separate-design`, `no-go`, `pending-measurement`, `unsupported-host`; ни одно решение не включает GPU в продукт автоматически.

- [ ] До работы зафиксировать объём и предел затрат: до двух инженерных дней на сбор доказательств. Нет доступного GPU host — записать unsupported/pending, без замены измерений догадками. Прототип в текущем задании по планированию не запускать.
- [ ] Выписать обязательные возможности и bytes каждой границы: grid/rays/input state, история материала шины, результаты элементов, каноническое суммирование и зависимости полного шага. Зафиксировать точные CPU executable/provider/config и SDK/device identity будущего опыта.
- [ ] Заранее записать критерии H1/H2/H3 и проверки точности из таблицы ниже. Сравнивать полные задержку/производительность, отдельно construction/setup/transfer и повторяемость; одного kernel time недостаточно.
- [ ] Изучить API по актуальной официальной документации выбранного SDK, указать version/date/URL. Если обязательная физическая возможность не поддерживается, соответствующая гипотеза получает no-go без установки ненужного стека.
- [ ] При позднейшем разрешённом измерении выполнить прогрев, ≥200 повторов микротеста и сравнение полной нагрузки с лучшим фактически измеренным квалифицированным CPU-вариантом. Показать распределение, не единственный лучший запуск.
- [ ] Применить критерии без изменения после получения результата. При положительном решении оценить отдельную стоимость реализации и полной физической квалификации; CPU остаётся default. Удалить временные hooks, случайно попавшие за пределы изолированного эксперимента.
- [ ] Провести независимое ревью доказательств и записки; свободный ADR номер использовать только для принятого архитектурного решения. Commit `docs(spatial): GPU evidence and bounded follow-up decision`.

Предлагаемый изолированный helper, определяемый этой задачей:

```cpp
namespace spatial_gpu {
bool latency_goal_met(double cpu_s, double gpu_s, bool accuracy_passed,
                      bool deterministic) {
    if (!std::isfinite(cpu_s) || !std::isfinite(gpu_s) || cpu_s<=0. || gpu_s<=0.)
        throw std::invalid_argument("positive finite measured times required");
    return accuracy_passed && deterministic && gpu_s <= cpu_s/2.;
}
}
bt::require(!spatial_gpu::latency_goal_met(10.,2.,false,true), "speed is not accuracy");
bt::require(spatial_gpu::latency_goal_met(10.,5.,true,true), "inclusive twofold goal");
```

Файл helper включает `<cmath>`/`<stdexcept>`, тест — существующий `migration_test.hpp` и выполняется внутри `bt::run`. Helper проверяет лишь арифметику решения; фактическую GPU-производительность он не доказывает.

**Acceptance:** записка разделяет измеренное, предполагаемое и неподдержанное, содержит воспроизводимые входы и обоснованное решение. **Failure/rollback:** отсутствие SDK/host/возможности или превышение бюджета записывается явно; скрытое ослабление CPU↔GPU арифметики и новые обязательные зависимости запрещены.

## Гипотезы и заранее заданные критерии

| Гипотеза | Что измеряется | Go-for-separate-design только если | No-go когда |
|---|---|---|---|
| H1: перенос rays/элементов одного шага | Dispatch + upload + kernel + суммирование + нужный readback + sync; весь затронутый tick | Полное время GPU-участка ≤0.5 лучшего квалифицированного CPU-участка **и** ускорение заезда ≥10%; прежние точность/детерминизм, без новой неограниченной задержки | Не выполнено хотя бы одно обязательное условие |
| H2: множество независимых эпизодов | Завершённые валидные эпизоды в секунду при одинаковых физике и данных | Производительность ≥20× лучшего измеренного CPU process batch и отдельно принятый объём реализации | Нет физической возможности, нужна несогласованная другая модель, ускорение <20× или затраты превышают заранее заданный бюджет |
| H3: автономная генерация/калибровка/анализ | Полная задача input→проверенный artifact, включая передачи и преобразования | Ускорение всей задачи ≥3×, результат проходит прежние точные и физические проверки | Узким местом остаётся CPU/I/O, ускорение <3× либо поддержка зависимости не оправдана редким использованием |

Бюджет H2 фиксируется до измерения по списку действительно переносимых модулей; старые «две недели» не считаются доказанной оценкой. Срок не отменяет физику и точность: при нехватке времени решение pending либо no-go с известными причинами.

## Минимальная форма записки

1. Вопрос и объём: интерактивная поездка, CPU batch либо автономный инструмент.
2. Точная текущая CPU identity и фактические размеры нагрузки.
3. GPU host/driver/SDK профиль или подтверждённая недоступность.
4. Источники матрицы поддержки, версии/даты, неподдержанные возможности.
5. Заранее заданные пороги и определения точности/детерминизма.
6. Измерения setup/dispatch/kernel/transfer/sync/полного запуска и распределения.
7. Сравнение с одним потоком и реально измеренным параллельным CPU-вариантом.
8. Решение каждой гипотезы и новый факт, который мог бы его изменить.
9. Изолированность прототипа и отсутствие изменений зависимостей продукта.

## Что этот документ не обещает

Задача не выбирает GPU backend для проекта, не переносит MuJoCo, не заменяет C++ ядро библиотекой Python и не обещает новую скорость. Переход на 3D завершается через S54 независимо от результатов S55. Если GPU полезен, последующий план начинается с отдельной спецификации точности/владения состоянием и проверки объёма поддержки macOS/Linux.
