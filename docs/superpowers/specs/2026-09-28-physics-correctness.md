# bikesim: спецификация физически согласованной продольной симуляции

Дата: 2026-09-28. Статус: проект спецификации для реализации и проверки.

**Базовая ревизия:** `vladmlch/bikesim@70623815b98788018bcdbd8eef347d778f9bb3f3`.

**Объект:** сцепление и деформация покрышек, массы и инерции велосипеда, взаимодействие райдера с велосипедом, подвеска, педалирование, центральный двигатель и трансмиссия.

**Источник текущего поведения:** исполняемые участки кода. Реестр [R01–R20](#реестр-референсов) содержит постоянные ссылки на проверенные диапазоны. Документация проекта, комментарии о результатах заездов и прежний аудит не являются подтверждением физической корректности. Документация MuJoCo используется только для семантики API движка.

**Граница выполненной работы:** эта спецификация не является патчем. Код репозитория и его тесты в рамках подготовки не запускались. Все новые допуски ниже — проектные критерии приёмки. Никаких результатов физических измерений или новых заездов документ не заявляет.

## 1. Цель, границы и уровни готовности

Цель — получить воспроизводимую модель, в которой нагрузки, ускорения, работа подвески и тяга возникают из согласованных сил и кинематических связей, а не из независимых поправок к скорости, развесовке или тангажу.

### 1.1. Обязательная область

Продольное движение в плоскости X–Z: X вперёд, Z вверх, ось вращения колёс +Y. Положительный `root_pitch` соответствует опусканию передней части. Плоская модель сохраняется; дополнительные боковые степени свободы не являются частью этой реализации. Существующее основание для этого — `root_x`, `root_z`, `root_pitch` [R19].

Покрытие неподвижно и жёстко. Поддерживаются горизонтальная поверхность, гладкий уклон, волнистый профиль, выпуклые кромки и впадины, если они проходят отдельную проверку контактной геометрии. Модель не должна приписывать себе достоверность для глубокого рыхлого грунта, бокового увода, виража, наклона велосипеда и деформации грунта.

Базовый двигатель — центральный: корпус на раме, выходной момент на шатунах/ведущей звезде. Задний мотор-колесо — другой тип силового пути и не должен незаметно подменять центральный двигатель.

### 1.2. Три уровня результата

**V0 — воспроизведение:** `legacy` сохраняет старую модель и старые контрольные сценарии. Его результаты явно подписаны как модель прежней ревизии.

**V1 — проверенная механика:** единые массы и инерции, корректные пассивные силы, раздельные контактные величины, исправленная подвеска, привод с физическими реакциями, согласованная запись мощности. Параметры могут оставаться синтетическими, но законы сохранения и численные проверки обязательны.

**V2 — калиброванная модель конкретной конфигурации:** пройдены V1 и независимые проверки по измерениям покрышек, подвески, развесовки и двигателя. Название реального компонента не повышает V1 до V2.

### 1.3. Не включать автоматически

Полную трёхмерную динамику, модель грунта, тепловую модель всей батареи, переключение передач под нагрузкой, подробную мышечную физиологию и автоматический выбор «оптимальных» настроек. Эти задачи не требуются для устранения перечисленных несогласованностей.

## 3. Обязательные архитектурные решения

### SYS-01. Отдельные режимы модели и привода

`physics_mode`: `legacy | physical`.

`drive_mode`: `coast | ideal_speed_control | crank_effort | articulated_effort`.

В `physical` режим по умолчанию — `coast`, воздушная помощь выключена. `ideal_speed_control` разрешён как испытательное воздействие; в отчёте обязательно `external_speed_controller=true`. Он не называется motor assist. Старые вызовы без `physics_mode` сохраняют `legacy` до отдельного изменения API по версии.

Комбинация `articulated_effort` требует физически связанного райдера. Существующий `seated` остаётся совместимым старым вибрационным вариантом, а новый называется `articulated_planar`. Неподдерживаемая комбинация отклоняется с `ValueError`, а не заменяется ближайшей моделью.

### SYS-02. Единая конфигурация и проверка конфликтов

Добавить неизменяемый `SimulationPhysicsConfig`, собираемый до компиляции MJCF. Он содержит режимы, параметры подвески, масс, шин/покрытия, трансмиссии, двигателя, аэродинамики и интегрирования.

`BikeSpecs` остаётся входом геометрии и совместимых настроек. Адаптер один раз переводит его в активные конфигурации. После этого силовые компоненты не читают независимые значения по умолчанию.

Существующие `controller=` и `coil_shock=` разрешены как явные overrides. При конфликте рабочего хода, длины/хода амортизатора или радиуса колеса конструктор завершается ошибкой с обоими значениями. Нельзя молча соединять геометрию 60 мм с bumper/HBO, рассчитанными на 65 мм.

### SYS-03. Владение силами и порядок шага

Сейчас writers присваивают отдельные элементы `qfrc_applied` [R01, R18]. С появлением цепи и контактных сил несколько компонентов будут писать в одни DOF. Для physical вводится общий `ForceAccumulator` с отдельными векторами вклада каждой подсистемы.

На каждом физическом подшаге:

1. Обновить кинематику и скорости в состоянии `q_n, v_n` средствами MuJoCo без интегрирования.
2. Очистить аккумулятор нового шага. Внешнее воздействие пользователя принять отдельным аргументом, а не сохранять случайные значения в `data.qfrc_applied`.
3. По текущей геометрии вычислить контакты собственного backend, если он включён. Для native backend предыдущие solver-нагрузки доступны только как явно устаревший управляющий snapshot.
4. Рассчитать подвеску, райдера, цепь, сопротивления и активные управляющие моменты. Каждый writer добавляет свой вклад, не затирая чужой.
5. Установить команды actuator и frictionloss тормозов. Выдать накопленные силы в `qfrc_applied`.
6. Зафиксировать снимок входного состояния, приложенных сил и мощности с временем `t_n`.
7. Вызвать `mj_step` один раз. Не менять `qpos/qvel` для устранения пробуксовки, растяжения цепи, отрыва или top-out.
8. Сохранить результат интервала `[t_n,t_n+h]`, отдельно от нового состояния `q_(n+1),v_(n+1)`. Обновить счётчики только один раз на интервал.

Первую версию реализовать через явный предшаг `mj_forward` перед чтением геометрии и обычный `mj_step`. Повторный forward допустим как стоимость корректности; оптимизация — отдельный PR после теста идентичности. Не менять интегратор скрытно переходом на `mj_step1/mj_step2`.

Пользовательские силы, вычисленные до `mj_step`, нельзя считать автоматически неявно интегрированными только из-за `implicitfast`. Жёсткость новых сил проверяется уменьшением подшага [E2].

### SYS-04. Полная наблюдаемость источников энергии

Для каждого активного/пассивного компонента сохранять фактически приложенную обобщённую силу и её мощность `Q @ qvel` в согласованный момент времени. Для собственных пружин сохранять потенциальную энергию.

Не считать `data.energy` полным запасом энергии: внешне вычисленные пружины и упругая цепь требуют собственных слагаемых. Записывать численный остаток баланса, не распределяя его автоматически на «сопротивление покрышек».

## 4. Подвеска

### SUS-01. Исправить обход HBO и разрыв Firm

**Референс:** `SuperDeluxeDamper.compute_damping_force`, [R03].

Сейчас ветвь Firm возвращает значение до добавления HBO. Новый порядок: основная характеристика Open/Firm → общий компонент HBO → сумма. HBO добавляется только при положительной скорости сжатия и ходе выше порога.

Сохранить низкоскоростной наклон `lockout_stiffness=15000 N*s/m`. В первой исправленной версии порог `v0=0.03 m/s`, сила перехода `F0=c_low*v0=450 N`. Заменить независимые 480 N на производное значение 450 N. Это осознанное изменение синтетической кривой, а не утверждение о реальном клапане. Формула верхней ветви: `F0 + c_high*(v-v0)`.

Приёмка: непрерывность силы в пределах `1e-3 N` при подходе к порогу на `1e-8 m/s`; `F_damper(v,s)*v >= -1e-10 W`; вклад HBO при одинаковых v и s одинаков в Open и Firm, если его параметры одинаковы. Не требовать `Firm >= Open` при всех скоростях: это не общий физический закон.

### SUS-02. Передать всю конфигурацию в активную подвеску

**Референсы:** создание компонентов [R01, R02, R04].

Единая фабрика создаёт `ForkAirSpring`, `BikeSuspensionSystem`, `CoilShock` и параметры ограничителей. Все клики `BikeSpecs`, преднатяг и жёсткость rear coil должны попадать в активные компоненты. В `BikeSuspensionSystem` добавить keyword-only ходы передней и задней подвески и передавать их демпферам.

HBO задавать относительным интервалом/длиной от конца хода: для совместимых defaults передняя зона 20 мм, задняя 20% хода. Для legacy оставить прежние абсолютные пороги. Валидация: длина зоны >0 и <= полного хода.

Приёмка: изменение каждого поддерживаемого параметра изменяет соответствующий результат силы или геометрии. Геометрические инварианты сравниваются отдельно; изменение клика не меняет массу модели.

### SUS-03. Корректное преобразование массы в калькуляторе

**Референс:** `_compute_shock_tuning`, [R05].

Принять `LR=dz_wheel/ds_shock`. В одномассовом приближении:

`m_eff_shock = m_eff_wheel * LR**2`;
`c_crit_shock = 2*sqrt(k_shock*m_eff_shock)`.

Это следует из равенства кинетической энергии при `v_wheel=LR*v_shock`. Исправление относится к калькулятору рекомендаций, а не автоматически ко всем коэффициентам активного демпфера. Не умножать работающий демпфер на LR² как компенсацию.

Добавить отдельную проверку приведённой жёсткости/демпфирования на колесе и именование выходных величин. Параметрический пример: 50 кг, LR=3 и k=100000 N/m дают приведённую массу 450 кг и критическое демпфирование около 13416.408 N*s/m. Число получено из формулы.

### SUS-04. Разделить coil, bumper и top-out

**Референсы:** [R06, R18].

Компрессионная coil-пружина:

`F_coil = k * max(s + preload, 0)`.

При отрицательном ходе и отсутствии преднатяга она не тянет. Bumper остаётся отдельной прогрессивной пружиной. Верхний ограничитель — отдельный компонент с собственным запасом энергии и демпфированием. Для `s<0` и координаты сжатия положительный `Q_top` возвращает шток к нулю; при `s>=0` он равен нулю.

Нельзя одновременно настраивать сильный собственный top-out и сильный solver-limit на той же рабочей области. Solver-limit остаётся аварийной границей за заявленной деформацией ограничителя. Его работу/нарушение писать отдельно. Не фиксировать прежние 7 мм выхода за ход как допустимый физический результат без измеренного top-out.

Начальный синтетический ограничитель определять через опорные силу и деформацию, а не коэффициент «на глаз»: `k_stop=F_ref/delta_ref`. Эти значения входят в конфигурацию и метаданные. Приёмка проверяет силу в опорной точке, пассивность и сходимость; ограничения реального железа появляются только из измерений.

### SUS-05. Сохранить правильный силовой путь, заменить неточную настройку sag

Сила штока прикладывается к `shock_stroke`, сила вилки — к `fork_travel`; дополнительного LR в динамическом writer нет [R18].

Для `--sag` использовать вложенный численный поиск давления и rear spring rate с вызовом существующего решателя статического равновесия на скомпилированной системе. Аналитический калькулятор даёт начальное приближение, но не финальный ответ. Остаток оптимизации: два отклонения от целевых ходов, измеренных в заданной позе. Границы поиска задаёт конфигурация; недостижимая цель возвращает диагностируемую ошибку, а не крайнее значение с подписью «успех».

Изменение масс, высоты/позы райдера требует нового равновесия. Прежние 30/30% не являются обязательными физическими defaults. Приёмка: ошибка достигнутого sag <=0.5 мм и остаток статической силы/момента в критериях раздела 10.

Воздушную пружину не переписывать без стендовых данных. Проверять положительность объёмов, область давления, допустимое число токенов и согласованность энергии с интегралом силы. Термическое различие статического и быстрого сжатия описать в данных калибровки; фиксированный показатель политропы — явно ограниченная аппроксимация.

## 5. Массы, инерции и развесовка

### MASS-01. Один бюджет физических масс

**Референсы:** аналитический бюджет [R08], геометрии колеса и шатунов [R07, R13].

Все поля `BikeMassSpecs` должны влиять на скомпилированные массы своих компонентов. Промежуточные массы геомов задавать как нормированные доли бюджета компонента либо задавать единый `<inertial>` тела. Нельзя одновременно использовать конкурирующие физические массы геомов и явного inertial без проверки правила компилятора.

Каждый компонент имеет стабильный идентификатор, массу, положение CoM, тензор инерции и происхождение параметров. Рама может объединять несколько компонентов: её итоговый inertial собирается через теорему параллельных осей. Масса райдера никогда не входит одновременно в раму и в отдельные rider bodies.

Для неподвижных относительно друг друга геомов внутри одного тела допустимо распределение массы по визуальной геометрии, если оно явно выбрано как synthetic. Визуальные изменения не должны незаметно менять инерцию physical-модели. Сохранение прежней картинки не требует сохранения прежней физической инерции.

### MASS-02. Физическая инерция колёс

Сейчас аналитический helper учитывает наружное кольцо, а MJCF переднего колеса создаёт массивные сплошные цилиндры [R07, R08]. Новая инерция задаётся явно и проверяется после компиляции.

Для кольцевого цилиндра вокруг +Y:

`Iyy = m*(r_outer**2+r_inner**2)/2`;
`Ixx = Izz = m*(3*(r_outer**2+r_inner**2)+width**2)/12`.

Суммировать обод, покрышку, втулку, кассету и ротор с их смещениями. Допускается более простое калиброванное кольцо+ядро, но оно должно быть тем же расчётом, который использует MJCF. Прежний helper не является измерением и не задаёт обязательное целевое число.

Проверки: положительная определённость тензора; неравенства треугольника для главных моментов; совпадение массы/CoM/тензора скомпилированного тела с конфигурацией; `alpha=T/I` на отдельном закреплённом стенде; вращательная энергия `I*omega**2/2`. Не брать диагональ полной матрицы M как безусловную инерцию свободно связанного колеса: подвижность родителя меняет эффективный отклик.

### MASS-03. Развесовка — результат динамики

Динамический CoM вычислять по `body_mass` и мировым `xipos` всех физических тел. Аналитический CoM ненагруженной геометрии сохраняется только как отдельная справочная величина.

Для статической горизонтальной проверки с общим весом W, задней точкой контакта xr и передней xf:

`Nf=W*(x_com-xr)/(xf-xr)`;
`Nr=W-Nf`.

Для наклона и динамики использовать полные уравнения внешних сил и моментов, а не эту формулу вне её области. Вертикальные реакции, нормальные реакции и касательные силы хранить отдельно.

Не добавлять ручную `m*a*h/L` силу к уже работающей многотельной модели. Формула допустима как проверка квазистатического предела на специальном стенде, с учётом фактического источника продольной силы.

## 6. Контакт покрышек и сопротивления

### TIRE-01. Разделить геометрию, физическую нагрузку и управляющий сигнал

**Референсы:** [R07, R09, R10].

Снимок контакта каждого колеса содержит `time_s`, идентификатор интервала, backend, точки контакта, нормали, нормальные силы, мировую результирующую силу, момент относительно оси, касательную скорость, эффективный радиус и признаки геометрического/нагруженного контакта. Не использовать название `support_n` для нескольких физических смыслов.

Обязательные агрегаты: `normal_load_n=sum(Fn_i)`; `world_force_n=sum(F_i)`; `vertical_force_n=world_force_n[2]`; `normal_vertical_n=sum(Fn_i*n_i[2])`; `tangent_force_n` по определённой продольной касательной. Вертикальный вклад трения на склоне нельзя терять в общем балансе веса.

Фильтр контакта возвращает только `controller_grounded`. Он не заменяет нагрузку и не создаёт контактную силу. Параметр задержки задаётся в секундах; повторное чтение того же timestamp не продвигает состояние. Для физических метрик airtime использовать сырой сигнал и отдельно показывать чувствительность к порогу.

`catch_plane` считается аварийным выходом из рабочей поверхности, а не обычной дорогой, вновь включающей привод.

### TIRE-02. Не приравнивать solref к материальной жёсткости

Отрицательный `solref` задаёт параметры опорного ускорения ограничения с масштабированием через impedance. Поэтому `-130000 -800` нельзя объявлять параметрами покрышки `130000 N/m` и `800 N*s/m` [R07, E1].

Сохранить native backend как `native_reference`. Его параметры описывать в единицах solver, а эффективную осадку измерять на отдельном стенде. Он может использоваться в V1 только для явно указанного диапазона нагрузок и сценариев, который проходит критерии, и не выдаётся за измеренную характеристику шины.

Добавить `compliant_2d` как независимый backend с собственным радиальным законом в физических единицах. Он должен полностью владеть силами колеса о дорогу: колесо–terrain исключается из native contact, иначе силы и трение учитываются дважды. Native collision рамы/руля об окружение остаётся для аварийных событий.

Backend выбирается явно. Непройденная калибровка или неподдерживаемая геометрия не вызывает скрытого переключения на другой backend.

### TIRE-03. Минимальный пассивный закон шины

В `compliant_2d` геометрический слой возвращает `penetration_m`, нормальную скорость и общую точку приложения. Нормальная сила при `delta>0`:

`Fn=max(0, k_z*delta+c_z*delta_dot)`.

При `delta<=0` сила равна нулю независимо от скорости. Энергия радиальной пружины `U_z=k_z*max(delta,0)**2/2`. Табличная монотонная нелинейная характеристика может заменить линейную без изменения интерфейса; энергия тогда равна интегралу этой характеристики.

Давление — вход выбора/интерполяции калиброванной характеристики. Не вводить универсальное `k proportional pressure` без данных. Таблица хранит реальные единицы, диапазон давления, нагрузок и температуру/условия опыта. Экстраполяция за диапазон в режиме calibrated запрещена.

Для касательного контакта первой версии использовать упругий элемент с релаксацией и ограничением силы. Его состояние xi имеет единицы метров:

`lambda=abs(v_roll)/relaxation_length_m`;
`xi_trial=(xi+h*u)/(1+h*lambda)`;
`xi_new=clip(xi_trial, -mu*Fn/k_x, +mu*Fn/k_x)`;
`Fx=-k_x*xi_new`.

Здесь `u` — скорость поверхности колеса относительно дороги в точке контакта, а не разность только `root_x` и hinge speed. При нулевой скорости качения контакт может сохранять статическую упругую касательную силу. При исчезновении контакта xi сбрасывается; удалённая энергия учитывается как потеря, а не исчезает из отчёта. До ограничения непрерывный закон удовлетворяет `P_contact+dU_x/dt=-k_x*lambda*xi**2 <=0`; дискретная версия проверяется отдельным энергетическим тестом.

Это модель эквивалентного пятна контакта, а не точная Pacejka-кривая и не модель всех грунтов. Падение трения после пика не добавлять без измерений. Ограничивать нужно силу контакта, а не входной момент двигателя: реальная пробуксовка должна оставаться возможной.

### TIRE-04. Геометрия контакта на профиле

Источник профиля — тот же дискретизированный terrain, который используется при визуализации/экспорте, с тем же преобразованием в мировые координаты. Нельзя вычислять силы по исходной гладкой функции, а рисовать/сопоставлять их с другим heightfield.

Первый алгоритм: ближайшая точка окружности к локальной ломаной профиля в диапазоне `center_x±radius`, с проверкой концов сегментов. Выбирать наибольшую положительную деформацию; копланарные дубликаты объединять. В точке равных кандидатов сохранять предыдущую ветвь до её геометрического выхода, не удерживая прежнюю силу. Нормаль идёт от дороги к центру колеса. На выпуклой вершине нормаль радиальная, а не нормаль произвольно выбранного соседнего треугольника.

Одна эквивалентная опорная область — объявленное ограничение `compliant_2d`. Если две раздельные поверхности одновременно дают значимый контакт с существенно разными нормалями, ставить `multi_support=true`; такие интервалы не входят в V2-выводы о пиковых нагрузках без отдельного многоконтактного стенда. Сами интервалы не удалять из данных и не маскировать удержанием нагрузки. До проверки этой области native_reference остаётся сравнительным backend, но не скрытым fallback.

Критерии геометрии: инвариантность плоского контакта к дроблению сегмента; контакт с кромкой раньше попадания центра над ней; отсутствие контакта через пустоту шире достижимой окружностью; непрерывность положения контакта на гладком профиле; конечные силы/импульсы на границе сегментов. Для острых кромок сравнивать импульсы и фильтрованные ускорения, а не требовать сходимости одного максимального отсчёта силы.

### TIRE-05. Три различных угловых скорости

`omega_wheel_abs`: абсолютная угловая скорость колеса в мире; нужна контактной кинематике и моменту взаимодействия шина–дорога.

`omega_wheel_rel`: скорость колеса относительно вилки/заднего звена; нужна работе соответствующего brake/hinge actuator.

`omega_crank_rel`: скорость шатунов относительно рамы; нужна механической мощности человека и центрального двигателя на выходном валу.

Нельзя заменить все три чтения одним «исправленным omega». Существующая запись мощности через hinge velocity [R16] соответствует мощности того actuator; ошибка заключается в её интерпретации как батарейной или человеческой мощности и в несогласованной временной выборке, а не в самом применении относительной скорости.

### TIRE-06. Сопротивление качению и аэродинамика

На одиночном наклонном контакте `Trr=Crr*Fn*R_eff`, а не `Crr*(Fn*n_z)*R_eff`. Текущий код использует вертикальную проекцию [R10]. В многоконтактной области не суммировать автоматически все силы удара как квазистатическую нагрузку покрышки: экспортировать raw и effective rolling load, алгоритм формирования последней и долю ограниченных отсчётов.

Сопротивление шина–дорога — внешнее взаимодействие. При явном моменте качения применять его к колесу в мире через `mj_applyFT`; не создавать неявно равный противоположный момент на `seatstay`, как при записи только в wheel hinge. Подшипниковое сопротивление, напротив, внутреннее и остаётся на relative hinge. Для движущейся дороги потребовалась бы явная противоположная реакция на неё; здесь мир неподвижен.

`Crr` калибровать по ровному выбегу вместе с радиальным/касательным гистерезисом: одна и та же потеря не должна оплачиваться дважды. Удалить физически немотивированный cap после калибровки либо оставить его только как диагностируемый выход за область достоверности, не как незаметную коррекцию.

Аэродинамическая сила: `F=-0.5*rho*CdA*|v_rel|*v_rel`, в плоскости X–Z, в заданной точке приложения. Не использовать исключительно `root_x`, если есть значимое вертикальное движение или ветер. При неподвижном воздухе сила пассивна; при ветре воздух может передавать энергию, поэтому это внешний энергетический канал.## 7. Педалирование, трансмиссия и motor assist

## 7. Трансмиссия, педалирование и motor assist

### DRIVE-01. Явная кинематика шатунов и кассеты

**Референсы:** неподвижные геомы шатунов [R13], прямой wheel actuator [R01], регулятор скорости [R14].

В physical создавать `crank` с hinge `crank_spin` на раме, `cassette` с hinge `cassette_spin` на заднем несущем звене, отдельное заднее колесо и педали на концах шатунов. Массу кассеты вынести из rear wheel, массу шатунов/педалей — из рамы, без удвоения общей массы. Педальная платформа может вращаться относительно шатуна; интерфейс ноги использует её фактическую поверхность.

Для сглаженной цепной модели шаг цепи p и число зубьев Z определяют средний кинематический радиус `r=p*Z/(2*pi)`. Это обеспечивает точное отношение по зубьям без моделирования полигонального эффекта. Числа зубьев и p входят в конфигурацию; по умолчанию synthetic-пример: p=0.0127 м, передняя звезда 34, задняя 24. Для сравнения передач использовать отдельные заезды с фиксированной передачей. Мгновенно менять отношение на ходу в первой версии запрещено.

### DRIVE-02. Передача силы через цепь, а не только wheel torque

При неподвижной геометрии и включённой муфте в идеальном пределе:

`omega_wheel_rel = (Z_front/Z_rear)*omega_crank_rel`;
`T_wheel = T_crank*(Z_rear/Z_front)`.

Однако это только стендовый предел. Для подвески нужна зависимость натянутой ветви от геометрии. Реализовать скалярную координату удлинения e и её полный якобиан J относительно обобщённых координат. Генерализованная сила цепи:

`Q_chain = -T_chain * J`, где `J = de/dq` и `e_dot=J @ qvel`.

Использовать упругую натянутую ветвь `T=max(0,k_chain*e+c_chain*e_dot)` при наличии зацепления. Свободная нижняя ветвь с натяжителем не передаёт равную верхней тягу; её малую преднатяжку в первой версии считать нулевой и явно указать это ограничение. Для больших нагрузок и анализа anti-squat такое приближение проверяется отдельно.

Геометрическая координата строится по общей внешней верхней касательной двух окружностей, включая изменение дуг охвата. Одно только расстояние BB–rear axle недостаточно. В плоскости X–Z, при центрах c_f,c_r, d=|c_r-c_f|, a=r_f-r_r, общей наружной нормали n и непрерывном полярном угле psi этой нормали:

`L_eff=sqrt(d*d-a*a)+a*psi`;
`e=L_eff-L_eff_ref + r_f*theta_front_abs-r_r*theta_cassette_abs - phase_ref`.

Углы theta положительны вокруг +Y; psi положителен в обычной системе atan2(z,x), то есть в противоположном направлении. Верхнюю касательную выбирать в системе рамы; угол psi разворачивать непрерывно. При общем жёстком повороте велосипеда члены должны взаимно сокращаться. В реализации разрешается эквивалентная запись полностью в системе рамы, если пройдены те же тесты.

В качестве проверки якобиана использовать центральную конечную разность с согласованным разворачиванием углов; рабочую реализацию можно сделать аналитической. При d<=|a| геометрия недопустима, возвращать `ValueError`.

Критерии: `Q_chain @ qvel == -T_chain*e_dot`; при отсутствии демпфирования изменение упругой энергии компенсируется работой; общий перенос/поворот системы не меняет e; силы цепи не создают результирующий внешний момент. Тестировать влияние замороженных шатунов/муфты на реакцию подвески. Не задавать целевое значение anti-squat числом без независимого расчёта геометрии.

### DRIVE-03. Обгонная муфта

Муфта связывает кассету и rear wheel, а не rear wheel с миром. Она передаёт положительную тягу и допускает обгон кассеты колесом. Для момента +T на колесе применяется -T на кассете.

Допустимая первая модель — односторонняя упругая угловая связь с отдельным состоянием точки зацепления, нулевым synthetic-backlash и пассивным демпфированием. При обгоне сохранять свободное вращение, не обнулять скорости тел. Освобождение упругой энергии отражается в балансе. Зубчатый backlash и детали храповика не нужны для V1.

Приёмка: вращающееся колесо не заставляет стоящий crank вращаться вперёд при свободном ходе; положительная тяга замыкает связь; обратное педалирование не создаёт прямую положительную тягу; торможение wheel при отключённой муфте не прикладывает фиктивный torque к раме двигателя. Backdrive при обратном движении проверять по выбранной кинематике муфты, а не запрещать все отрицательные скорости.

### DRIVE-04. Два честно названных режима усилия человека

`crank_effort`: момент задаётся на `crank_spin`, с реакцией на раму. Это эквивалентный силовой стенд. Он позволяет исследовать передачу средней тяги, но не заявляет достоверную педальную раскачку от ног.

`articulated_effort`: момент формируется суставными actuator райдера и силами ноги–педаль. Дополнительный «человеческий» момент на crank при этом запрещён: иначе работа человека учитывается дважды. Моторный момент на crank остаётся разрешён.

Вход команды — желаемое среднее усилие/мощность, положительное направление педалирования и целевой каденс. Для старта использовать ограниченный момент, не `P/omega` с бесконечностью в нуле. В режиме torque-source допускается профиль `T_mean*(1-a*cos(2*theta))`, `0<=a<1`; среднее по фазе равно T_mean, но средняя мощность при неравномерном каденсе вычисляется по фактическому моменту и скорости.

Приёмка: ненулевой момент возможен при нулевом каденсе, но механическая мощность в этот момент равна нулю; среднее по циклу проверяется численно; ограничение момента не меняет знак вращения принудительно.

### DRIVE-05. Контроллер помощи двигателя

Контроллер не получает ошибку cruise-speed как главный вход. Входы: измеренный положительный момент педалирования, каденс, выбранный assist gain, скорость датчика, тормоз, доступная энергия. Выход: момент на выходном валу центрального мотора.

`T_request = assist_gain * max(T_human_measured,0)`;
`T_limit = min(T_max(cadence), P_mech_max/abs(omega_crank_rel))` вне нуля;
`T_command = min(filtered_request,T_limit)*speed_taper`.

У нуля ограничение по мощности не используется вместо ограничения по моменту. Фильтр первого порядка и ограничение скорости изменения момента работают в секундах и N*m/s. После фильтра повторно применяются мгновенные пределы мощности и момента. Тормоз имеет высший приоритет: момент становится нулевым на текущем шаге, накопленное состояние фильтра сбрасывается. Пропадание положительного педалирования отключает помощь в заданное время `pedal_stop_delay_s`; оно не определяется контактом rear wheel.

Стартовая synthetic-конфигурация для тестов, не характеристика конкретного мотора: gain=2; предел 80 N*m; механическая мощность 500 W; каденс включения 10 rpm и выключения 5 rpm; time constant 0.05 s; torque slew 400 N*m/s; прекращение педалирования 0.10 s. Порог скорости задаётся конфигурацией; пример 25 km/h — сценарное число, не утверждение о законодательстве или реальном контроллере. Зона taper задаётся отдельной шириной и должна быть непрерывной.

Источник скорости задавать явно: `wheel_sensor` либо `ground_truth_test`. Для wheel_sensor использовать измеряемую относительную скорость wheel sensor и номинальный радиус; для тестового ground truth — фактическую продольную скорость по поверхности. Не смешивать их при пробуксовке.

Отрицательный моторный момент и рекуперация отсутствуют в первой центральной модели с обгонной муфтой. На спуске мотор отключается, а не автоматически удерживает скорость. Исключение — явно включённый `ideal_speed_control`, чья работа учитывается отдельно.

### DRIVE-06. Потери и батарея

Выходной механический момент не умножать на КПД повторно, если он уже задан как момент на выходном валу. Электрическую мощность вычислять из выходной механической и модели потерь.

Минимальная synthetic-модель: `P_elec=max(T_motor*omega_crank_rel,0)+a*T_motor**2+b*omega_crank_rel**2+P_idle`, пока мотор включён. Это даёт ненулевые потери при удержании момента на малой скорости. Коэффициенты a,b и idle задавать явно; они не являются заводской картой эффективности. Измеренная карта заменяет эту модель через тот же интерфейс.

`energy_remaining_j=max(0,energy_remaining_j-P_elec*h)`. При исчерпании энергии torque=0. Энергию, которую батарея уже не могла отдать внутри последнего шага, нельзя записать как фактически полученную: ограничить доступную электрическую работу и соответствующий момент/подшаг в момент отключения. Модель battery storage хранит Joules; Wh — только формат отчёта.

Механические потери цепи/подшипников отдельны от электрических. Любая их аппроксимация обязана иметь неотрицательную рассеиваемую работу. Для аналитического теста передачи все потери отключаются.

### DRIVE-07. Статическое торможение и отключение тяги

Сейчас тормозной момент исчезает при нулевом hinge speed [R01]. В physical реализовать сухое трение в wheel hinge через `dof_frictionloss`, с пределом от команды ручки, либо эквивалентное ограничение скорости с ограниченным моментом. Не использовать одновременно этот механизм и прежний taper torque.

Тормоз реагирует на относительное вращение колеса и его несущего тела; это правильная внутренняя реакция. При чтении фактической brake power использовать фактическую силу ограничения и relative speed. Заданная ручкой максимальная величина не равна постоянно приложенному моменту.

В physical любой ненулевой brake demand отключает motor assist и положительную тягу ideal_speed_control. Человеческая мышечная работа может быть отдельно задана исследовательским сценарием, но по умолчанию пользовательская команда тормоза отменяет целевое педалирование. Приёмка: удержание на уклоне при достаточном тормозном моменте без постоянного ползучего вращения; конечные силы при переходе к скольжению; отсутствие самопроизвольной смены направления от тормоза.

## 8. Физически связанный райдер

### RIDER-01. Анатомические массы не зависят от опорных долей

**Референсы:** перераспределение масс по shares [R12] и независимые slider bodies [R11].

Новый `articulated_planar` использует постоянные анатомические массы. Желаемые доли опоры могут входить в управление позой, но не меняют массу головы, рук или ног. Координаты CoM и инерции сегментов хранятся отдельно от внешнего вида. Старый `seated_path_masses` не используется новым builder.

Массу шлема учитывать ровно один раз. Связанные части должны сохранять полную массу при переходе между сидением, стойкой и разгрузкой. Исходные антропометрические пропорции из кода допускаются как prior, а не как персональное измерение.

### RIDER-02. Минимальное связанное дерево

Таз — самостоятельное плоское тело в worldbody с координатами X, Z, pitch, а не child рамы с единственным slide. Торс связан с тазом hip/torso hinge. Каждая нога: бедро → голень → стопа, с тазобедренным, коленным и голеностопным суставами. Пара рук может быть представлена одной эквивалентной двухзвенной цепью от торса к рулю для чисто продольной задачи. Голова закреплена на торсе с физически заданной массой/инерцией.

Поза из текущего solver используется как начальное геометрическое приближение, но после старта не присваивается каждый шаг. Все движения создают суставные силы/моменты и реальные реакции.

Коллизии райдера с дорогой включать только для выбранных аварийных геомов, а не для всех визуальных капсул. Падение/удар ноги не следует автоматически считать невозможным из-за прежнего отсутствия rider-ground collision.

### RIDER-03. Интерфейсы с велосипедом

Седло может толкать таз, но не тянуть его обратно. Плоская педаль толкает стопу и передаёт ограниченную силу трения. Рука в режиме grip может передавать оба знака силы; отпускание grip размыкает связь. В первой версии нет пристёгнутых педалей, поэтому вертикальная тяга отрывающейся стопы запрещена.

Для нормальных контактных сил использовать реальную геометрию gap. Для касательной податливости использовать состояние относительного смещения в контактной точке и ограничение трением. Силы реакции прикладывать к обоим телам в общей точке контакта. Для пары сил в разных точках проверять результирующий момент: равенство сил само по себе не гарантирует сохранение углового момента, если силы не центральные.

Полные force/wrench интерфейсов записывать отдельно от внутренних суставных реакций. Нулевой saddle force должен означать отсутствие механической опоры седла, а не сохранение скрытой продольной направляющей. При одновременно разомкнутых седле, педалях и руках райдер и велосипед движутся независимо; разрешены только внутренние ограничения каждого из двух объектов.

### RIDER-04. Управление позой и педалирование

Управление — ограниченные суставные моменты, а не внешняя сила на root. Нейтральную позу удерживает PD с явными лимитами момента и скорости/мощности, параметры synthetic до калибровки.

Для педалирования задавать фазу и целевую касательную силу стопы на педаль. Суставные моменты вычислять через якобиан ноги с учётом позы и допустимого контакта. На опорной фазе `tau_leg=J_foot.T @ F_target` с согласованным знаком «стопа действует на педаль»; гравитационная/постуральная компенсация — отдельный наблюдаемый активный вклад. На переносе стопы нет тяги через потерянный контакт. Если геометрия не позволяет требуемую позу, контроллер насыщается и сообщает ошибку, не удлиняет сегменты.

Механическую работу человека считать суммой фактических работ суставных actuator. Мощность, доставленная шатунам, отдельно измерять через pedal forces и crank velocity. Их разность содержит изменение энергии тела и потери, а не обязательно ошибку баланса.

Физическое управление тангажом в полёте допускается только внутренними движениями райдера и/или изменением вращения колёс. Прежний `PitchStabilizer` [R15] запрещён в physical независимо от выбранного rider variant.

## 9. Данные и внешний интерфейс

### DATA-01. Формат конфигурации и метаданные

В `summary.json` сохранять `schema_version=2`, `physics_revision`, commit модели, фактические версии Python/MuJoCo/NumPy/SciPy, dt, controller interval, seed, хеш профиля поверхности, полную разрешённую конфигурацию, backend шин, drive mode, rider model и calibration status.

Новые CLI-параметры: `--physics legacy|physical`, `--drive coast|ideal_speed_control|crank_effort|articulated_effort`, `--physics-config PATH`, `--initial-speed KMH`, `--human-torque NM`, `--assist-gain VALUE`, `--timestep S`. Сложные параметры задаются TOML, не десятками отдельных флагов. `--speed` остаётся только целевой скоростью идеального регулятора. Передача `--speed` для coast/effort возвращает ошибку с указанием `--initial-speed`.

В `legacy` неизменённый вызов CLI сохраняет старое поведение. В `physical` отсутствие drive означает coast и требует ненулевой `--initial-speed` для автоматического заезда до конца трассы либо явного ограничения времени. Неподвижный физический стенд не считается ошибкой только потому, что не доехал до финиша.

### DATA-02. Телеметрия без смешения физических смыслов

В новой строке данных хранить время состояния и время силового интервала. Не брать силы, вычисленные на `q_n`, умножать их на скорость `v_(n+1)` и подписывать как строго мгновенную мощность. Для интегрирования работы использовать согласованную квадратуру; для первой версии разрешён левый прямоугольник с отдельной оценкой ошибки по dt.

Обязательные группы каналов:

- Шины: raw/geometric/controller contact, Fn, полная мировая сила, penetration, u, kappa, R_eff, omega_abs, omega_rel, энергия и потери контактных элементов, признак multi_support.
- Массы: общий CoM и масса, фактические положения осей/контактов, передняя/задняя нормальные и вертикальные силы.
- Подвеска: coil/air, damper, HBO, bumper, top-out, solver-limit отдельно; ход, скорость штока, запасённая энергия, остаток замыкания linkage.
- Привод: каденс, фаза crank, передача, chain extension/tension/power, состояние freehub, human input, motor output, electrical power, battery energy, фактическая brake power.
- Райдер: фактические контактные wrench седла/педалей/руля, gap, суставные работы, положения и скорости CoM.
- Баланс: кинетическая энергия всей системы, гравитационная потенциальная, собственные упругие энергии, внешняя работа, активная работа, диссипация и необъяснённый численный остаток.

`wheel_power_w` старого формата не переименовывать незаметно в battery power. Старые читатели получают адаптер или остаются на schema_version=1. Поддержка нового формата в HUD/plots должна брать значения из тех же снимков, что CSV/JSON.

Использовать независимые ожидаемые результаты: аналитический одноосный стенд, виртуальную работу, внешние уравнения равновесия и измерения. Тест, который повторяет ту же формулу реализации, не является единственным доказательством.

## 11. Измерительная калибровка и область достоверности

Для V2 требуется набор данных с происхождением, датой, единицами, конфигурацией и неопределённостью измерений. Минимальные наборы: wheel load–deflection при нескольких давлениях; force–velocity/force–travel подвески; общий вес и нагрузки на весах под колёсами в заданных позах; момент/мощность двигателя относительно каденса; плоский выбег.

Данные делить на fit и holdout по целым экспериментам, а не случайным отсчётам одной записи. Калибровка не использует будущие holdout-сигналы. Сначала идентифицировать подсистемы на стендах, затем систему целиком; иначе ошибка шины легко компенсируется демпфером.

Формат JSON: `dataset_id`, `source`, `measured_at`, `units`, `bike_config_hash`, `sensor_uncertainty`, `conditions`, `samples`, `split`. Строка `source="synthetic"` допустима только для synthetic-тестов. При отсутствующей температуре/давлении нельзя объявлять применимость вне условий опыта.

Флаг `calibrated` выставляется только при наличии отчёта holdout. До этого отчёт говорит `synthetic` или `parameterized_unvalidated`. Спецификация не требует придумывать отсутствующие измерения и не допускает скрытого выбора коэффициентов ради правдоподобной картинки.

## 12. Реализация, совместимость и выпуск

Планы в `../plans/` разделены по независимым результатам: ядро/подвеска, массы, контакт, трансмиссия, райдер и интеграционная валидация. Ведущий план содержит зависимости и матрицу покрытия требований.

Старые эталоны сохраняются под `legacy`. Новый physical baseline создаётся только после прохождения аналитических проверок. Изменение golden XML не является доказательством правильности физики.

Каждый PR включает red/green test, фактическую конфигурацию, описание изменившегося физического смысла и локальные результаты проверки. Репозиторий не изменяется этой спецификацией; команды commit в планах предназначены для будущего исполнителя.

Условие готовности V1: выполнены SYS/MASS/SUS/DATA, DRIVE-01..07, TIRE-01..06 в заявленной области выбранного backend, тесты A01..A23 для поддерживаемых сценариев. `articulated_effort` публикуется только после RIDER-01..04. До этого разрешён `crank_effort` с явной пометкой отсутствия достоверной биомеханической педальной раскачки.

- E2: [MuJoCo Computation](https://mujoco.readthedocs.io/en/stable/computation/index.html) — обобщённые силы, Jacobian, интегрирование и friction loss.

- E4: [MuJoCo XML reference](https://mujoco.readthedocs.io/en/stable/XMLreference.html) — inertial, condim и joint frictionloss.
