# Анатомия времени шага: что реально устранит нативный код

Type: research
Status: resolved
Blocked by: —

## Question

Куда уходит wall-time физического шага сегодня, и какая его доля принципиально устранима нативным кодом? Разложить на: `mj_step` (уже C), контроллер райдера + `allocate_effort` (scipy SLSQP), пер-шаговые физические вычисления вокруг движка (tyre, контакты, drivetrain, energy checks), запись/диагностика. Для каждой формы (stay-post-P / гибрид / полный) дать оценку потолка выигрыша: какая доля wall-time вообще адресуема портом оркестрации.

## Context pointers

- Профиль из P-плана: `docs/superpowers/plans/2026-10-03-v2-01-performance.md` (56с стены; `rider_control.compute` 44.5с; `allocate_effort` 39.6с, ~9604 SLSQP; recorder 5.4с; `settle_welds` 3.1с).
- Замер: `tools/measure_realtime.py`.
- Горячий путь: `src/bike_sim/sim/ride/physical_runtime.py`, `src/bike_sim/sim/ride/rider_control.py`, `src/bike_sim/physics/rider_allocation.py`, `src/bike_sim/sim/ride_sim.py`.
- Формы и ограничения: `.scratch/cpp-port/map.md` (Notes).

## Constraints

- Стоимость/трудоёмкость порта не оценивать — только технический потолок выигрыша по скорости.
- Baseline — два столбца: текущий код и пост-P-plan (1 QP на тик вместо ~12 на шаг).

## Answer

### Замер на HEAD (собственный, воспроизводимый)

Команда: `uv run python` + `build_physical_simulation_from_args` на `examples/research/rough_uphill_extreme.toml` + `examples/research/viewer_physics_welded.toml`, `dt=0.0005`, `decimate=80`, headless, 2000 шагов после прогрева. Модель: `nq=nv=26, nu=12, nbody=28, neq=7, nefc≈24` — крошечная система, вся стоимость в вызовах, а не в FLOPs.

- **1.80 мс/шаг, RTF ≈ 0.28** (без профилировщика). cProfile: 3.08 мс/шаг, ~6460 Python-вызовов и ~100 pybind-вызовов на шаг.
- Важно: прогон выдал `energy.constraint_work` warning (`model_valid=false`), т.е. цифра — анатомия, не валидный эталон.

### Разложение по категориям билета

**1. `mj_step` — уже C, порт даёт ~0.** 40 мкс/шаг, ~2% сегодняшнего шага (~4% от пост-P проекции 0.5 мс). Единственный выигрыш — если менять сам движок, вне скоупа.

**2. Прочие engine-вызовы (~190 мкс, ~10%) — уже C, адресуемы только числом вызовов.** `apply_forces` делает `mj_forward` 2 раза каждый шаг (`physical_runtime.py:243,318`) + ещё один на тике (`:300`) + один после `mj_step` (`:629`): движок пересчитывает всю pipeline после каждой записи `qfrc_applied`/`ctrl`. Это ~120 мкс чистого C-времени, частично устранимо через `mj_forwardSkip`/`mj_step1`+`mj_step2` — причём это доступно и из Python, т.е. выигрыш полу-нативный. 19 `mj_jac`/шаг — телеметрия связей (`attachment_wrench.py:45-53` — по 2 Якобиана на каждое из ~5 креплений) + по 2 на колесо + пад-сайты. `mj_name2id`/`mj_id2name` вызываются ~28 раз на шаг из Python-циклов (`physical_observations.py:113`, `physical_runtime.py:50`) — чистый мусор, убирается кэшем адресов.

**3. Пер-шаговая физика Python вокруг движка (~550 мкс, ~30%).** Шина `compute_qfrc`-писателей: шины-кисточки (`tire_forces.py:116`, `physics/tire.py:_brush_step`), пад-опоры райдера (`rider_contacts.compute_qfrc`, `_pads` — `_box_pad_contact` на каждый из 2 сайтов × опоры), трансмиссия (`drivetrain_forces._compute_components`, идеальные муфты `ideal_freehub`), подвеска (`forces.compute_qfrc_components` — ~8 векторов `np.zeros(nv)` на шаг), сопротивление, тормоза, `envelope_forces`. Всё — скалярный Python + крошечные numpy-вектора (nv=26): фиксированная стоимость вызова ~0.3–1 мкс доминирует над математикой. В C++ тот же объём — ~20–40 мкс/шаг. **Полностью адресуемо нативным кодом (~90–95% строки).**

**4. Контроллер райдера + `allocate_effort` (~70 мкс/шаг сейчас, ~4%).** Два режима:
- *Текущий дефолт (`pedal_attachment="spindle"`)*: с коммита `835a48c` `compute` (`rider_control.py:756`) — замкнутая форма `leg_crank_targets`/`split_joint_torques` (`crank_split.py`), **QP вообще нет**; 1.16 мс на тик → ~0.07–0.12 мс/шаг амортизированно. QP-строка из профиля билета к текущему дефолтному растению не относится.
- *Legacy-ветка (`_compute_legacy`, конфиги weld/flat-pedal)*: `allocate` (`rider_control.py:1331`) → `allocate_response` (`rider_response_allocation.py:81`) или инлайн-QP `n_z≈57` со ~150 неравенствами; лесенка усилия × ветви хвата × до 4 рестартов SLSQP. Профиль P-плана: `rider_control.compute` 44.5 с из 56 с (2400 шагов, dt 1.25 мс), `allocate_effort` 39.6 с / ~9604 вызова. По инструментальному профилю аудита (`docs/superpowers/audits/2026-10-03-realtime-after-P.json`, 9.56 allocation/тик, 95.5% стены): из 447.9 с в `_minimize_slsqp` **355.5 с — сам FORTRAN `slsqp` (75%), ~52.8 с — оценка ограничений из Python-callback, ~26 с — objective**, остаток — scipy-клей и сборка матриц. Т.е. даже «Python-QP» на 3/4 уже скомпилированный код: порт снимает ~20–25% (callback-обвязку + сборку) плюс алгоритмический выигрыш смены солвера (плотный active-set с тёплым стартом по nz≈34–57: ~20–80 мкс на решение в C++ → ~3–10× против SLSQP на этой размерности), но не «удаляет» строку. Пост-P проекция: 1 QP/тик ≈ 1–2 мс/тик → ~0.1–0.2 мс/шаг; нативно — ~5–8 мкс/шаг.
- `linprog`-префильтры (`rider_response_allocation.py:23`) — HiGHS, уже C. `pinv/lstsq` — LAPACK, уже C.

**5. Запись/диагностика/учёт (~1.0 мс/шаг, ~55% — самая большая строка сейчас).** `prepare_attachment_raw` (230 мкс/шаг: 10 `mj_jac` + `_pads` + геометрия на каждый шаг — дороже самого `mj_step`), `settle_welds` + `equality_rows` (множители связей → qfrc), `tire_channels` (словари + Якобианы), `energy_state`/`stored_terms` (энергия всех пружин каждый шаг), `constraint_components`/`numerical_constraint_powers` (разворот efc-строк), `sensor_channels`, `_loss_increment`, сборка `channels`/`diagnostics`-dict, `PhysicalSample`+`WorkHistory.add`+`model_status.observe`, и `_close_period` — пакетная оценка периода (`evaluate_attachments` со стеком `pinv`, `_effort_observations`, нарушения бюджетов). Запись CSV после P4 — колоночная и децимированная (recorder в `measure_realtime` вообще не вызывается; `write_csv` — финальный flush ~мс на весь прогон): пост-П `write_csv` перестал быть строкой расхода, в отличие от 5.4 с/9.6% в исходном профиле. **Почти всё адресуемо** (та же математика в компилированном коде ~10–30× дешевле), с оговоркой: контракт каналов и допусков эквивалентности обязывает считать те же величины — выигрыш «компиляция + ленивая материализация», не «не считать».

**6. Интерпретатор/GIL/binding.** ~6460 Python-вызовов/шаг + ~100 pybind-переходов + ~200 тыс. скалярных numpy-оп/шаг — это механизм, делающий строки 3–5 дорогими; отдельной строкой не считается, но в нативе пропадает целиком. Побочный эффект полного порта: исчезает GIL → in-process многопоточные rollout'ы для batch-исследований (в Python доступно только через multiprocessing; прирост throughput, не per-step RTF).

### «Нативный код не чинит» vs «нативный код снимает»

- **Не чинит:** `mj_step` (40 мкс), LAPACK в `pinv/lstsq/solve` (батч венчей, `ConstraintDynamics`), FORTRAN SLSQP (~75% старой строки QP), HiGHS `linprog`, собственно физику шага.
- **Снимает:** весь Python-клей шага (~1.6 мс из 1.8): писатели сил, телеметрию связей, энергоучёт, каналы/сэмплы, батч периода, замкнутый контроллер; pybind-обвязку (~100 вызовов); сборку QP и callback-и (~20–25% строки QP).
- **Полу-снимает (доступно и Python'у):** сокращение `mj_forward` 3→1–2 через `mj_forwardSkip`/`mj_step1,2` (~60–80 мкс/шаг), кэш `name2id`, ленивые каналы только на записываемых шагах. Т.е. часть «нативного» выигрыша — реструктуризация, не компиляция.

### Потолки по формам (dt=0.5 мс/шаг → RTF = 0.5/мс-шага)

Неустранимый остаток нативного шага: `mj_step` 40 мкс + 1–2 `mj_forward` 40–80 мкс + нативные писатели/телеметрия/учёт ~30–80 мкс + контроллер ~5–10 мкс (QP-вариант тоже ~5–8 мкс амортизированно) ≈ **0.12–0.25 мс/шаг**.

| Форма | Оценка шага | RTF | Адресуемая доля стены |
|---|---|---|---|
| stay (пост-P проекция) | 0.5 мс | **~1×** | — |
| гибрид (нативный горячий цикл, шаг за вызов из Python) | 0.16–0.28 мс (+10–30 мкс межъязыковый шов/шаг) | **≈1.8–3.0×** | ~85–90% от текущих 1.8 мс; ~70% от пост-P 0.5 мс |
| полный (весь рантайм C++, standalone/extension) | 0.13–0.25 мс | **≈2–3.5×** | то же + запись/диагностика без шва + потоки для batch-роллаутов |
| абсолютный пол (только `mj_step`+1 forward, телеметрия по требованию) | ~0.08–0.10 мс | ~5–6× теоретический максимум, недостижим без срезания контракта каналов |

Против **замеренного** 1.8 мс/шаг (RTF 0.28): гибрид/полный даёт ~7–12× ускорение. Против пост-P проекции 0.5 мс (RTF 1×): ~2–3.5×. Против исходного 23 мс/шаг профиля билета: ~100×, но этот компаратор нечестен — большая часть достигнута уже Python-изменениями (P-план + замкнутый контроллер).

Оговорки честности: (а) потолок зависит от трассы/режима контактов (это extreme; в полётах дешевле); (б) 3.5× — верх при 1 forward и минимальной телеметрии, 2× — консервативно; (в) детерминизм/эквивалентность каналов сохранится только при бит-в-бит переносе математики — потолок скорости от этого не меняется, но «лишние» оптимизации (параллельные редукции, другой QP-солвер) могут шевельнуть последние знаки.
