# Read-only physics audit

Scope: specific reviewer claims in chain geometry, profile/support geometry, suspension/brake/rider/tire/cruise writers, scalar parser, realtime/concurrency and duplicated math. No production edits and no broad builds/tests. Targeted subprocess scripts: `/private/tmp/physics-audit-repro.py`, `/private/tmp/physics-extra.py`, run using `UV_CACHE_DIR=/private/tmp/physics-audit-uv uv run --offline python ...`. Used existing native/build extension; direct observations match current sources, but not claiming a fresh native verification profile.

## Confirmed current contract differences

1. **Legacy fork HBO validation over-restricts valid Python input.** `native/src/writers/suspension.cpp:317-324` always requires `total_travel_mm-hbo_start_mm>0`. Python `src/bike_sim/physics/damper.py:167-190` gates HBO-zone validation on `not legacy_behavior` and legacy start is fixed at 160 mm. Native `Charger3Config` (`native/src/config.hpp:61-66`) discards that legacy flag; project emits resolved start. Repro Python `Charger3Damper(total_travel_mm=150,legacy_behavior=True)` constructs with start160, while changing projected legacy fork total to150 makes native Stepper reject with ValueError. Missing same check on legacy shock is intentional (`suspension.cpp:331-335`, Python damper.py:279-281); applying universal validation there would break compatibility too. Default legacy golden test is only shipped travel180 (`tests/reference/test_native_suspension.py:67-107`), so it misses this boundary. Verdict: real valid legacy-parameter parity bug.

2. **Air spring negative chamber hides a Python error.** `native/src/config.hpp:325-340` parses air specs without semantic validation, `suspension.cpp:65-70` runs libm pow and max0. Python `air_spring.py:21-33,64-73` likewise lacks spec validation, but negative ratio raised to gamma1.4 becomes complex and `float(p_neg)` fails (`air_spring.py:135-140`). Repro neg_chamber_length_mm=-5, fork travel10: Python TypeError complex→float; native fork spring=-0.0. `native/src/writers/pyfloat.hpp:14-16` is only platform std::pow, not Python's full exponentiation error/domain behavior. Verdict: real error-parity/masking issue for public malformed specs, not a missing validation uniquely introduced in native and not proof valid thermodynamics fails.

3. **Damper zero denominators become NaN rather than Python division errors.** `native/src/config.hpp:284-301` accepts max_lsc/max_hsc/max_reb=0 and v_knee_comp/v_knee_reb=0; `suspension.cpp:82-90,100,107,144,172` divides without guards. Python BaseDamper constructor is also unchecked (`damper.py:103-120`); subclasses supply fixed positive maxima/knees (`damper.py:172-186,257-271`). Hand-built native dict or mutating Python object's public attrs reaches zero. Repro max_lsc=0, lsc_clicks0: Python ZeroDivisionError versus native NaN fork_damper. Zero knees similarly differ. Verdict: real malformed-config parity failure; ordinary project() of unchanged Python subclass cannot introduce zero. Broad claim 'damper constructor has no validation' is false: native validates total travel, modern HBO zone, shock stroke; coil validation is extensive (`suspension.cpp:303-335`).

4. **NaN tire time maps to wrong exception.** `native/src/writers/tire.cpp:622-625` conflates NaN and infinity into overflow_error before snapshot validation; Python `tire_forces.py:180-184` evaluates builtin round and raises ValueError for NaN. Stepper public set_state accepts arbitrary time (`stepper.cpp:143,162`). Repro on pinned model shifted +0.6: native OverflowError 'cannot convert float infinity to integer'; live Python ValueError 'cannot convert float NaN to integer'. Both reject, state commits only at end (`tire.cpp:669-677`, Python tire_forces.py:201-205). Verdict: real exception parity bug, low practical impact.

5. **nearbyint depends on FENV.** `native/src/writers/tire.cpp:626` uses current rounding mode while Python builtin round is ties-even independent of FENV (`tire_forces.py:183`). Repro arm64 fesetround(0x400000)=FE_UPWARD, time0.003125 dt0.00125: native interval3, Python round(2.5)=2; with default rounding both2. Profile comments explicitly assume default FP (`tyre/profile.cpp:17`; writer tire.cpp:10). Verdict: real conditional parity mismatch; requires externally changed process FP rounding mode, not observed normal runs.

6. **Undocumented snapshot interval integer narrowing (extra finding).** `native/src/writers/tire.hpp:37` int64; `tire.cpp:627-630` rejects finite rounded values above9.2e18, which even excludes some valid int64 values below INT64_MAX≈9.22337e18. Python `contact_state.py:94-110` requires nonnegative Integral but has no upper limit, `tire_forces.py:183` builtin round creates arbitrary-sized int. Repro time1e20 dt.00125: native OverflowError; live Python returns interval80000000000000000000000. Both inputs are finite positive public set_state/dt. Verdict: real finite-input contract gap, huge times/tiny dt boundary rather than routine simulation failure.

7. **Boolean material scalars accepted (extra finding).** `config.hpp:225-226,437` casts True→1.0 and `tire.cpp:199-205` passes finite-positive checks. Python `physics/tire.py:14-16,52-54` explicitly rejects booleans as not real scalars. Repro native front.material.radial_k_n_m=True constructs; Python TireSpec(True,800,200000,'synthetic',(0,2000)) raises ValueError. Verdict: real public hand-built-config type-parity gap.

## Claims needing qualification / rejected defects

8. **chain buffer removes const: false.** `native/src/drivetrain/chain.hpp:34-36` takes T* and returns span<T>, so const T* infers const T and preserves const. No remove_const or const_cast. Note const mjModel* does not make its allocated pointees const (MuJoCo ABI pointer fields); that's distinct from removing const from T. Count sign is unchecked, yes: span/count view expects valid nonnegative extent. All actual counts are compiled MuJoCo mjtSize (chain.cpp:113,122,126; transmission.cpp:27-44); negative input requires violating internal model/helper preconditions. Constructor nv similarly trusted (`chain.cpp:104-108`). Verdict: the template preserves pointee const, but const mjData does not const-qualify its pointer members. Controller static_asserts confirm buffer(const double*,0) returns span<const double>, while buffer(const mjData*->qpos,0) returns span<mjtNum>. This is shallow-const API hardening, not an actual cast-away-const operation. Count validation is an internal precondition.

9. **Unchecked chain body/front/rear/frame IDs: technically true helper precondition, no public bad-ID path.** chain.cpp:113,123,155-160 creates unchecked subspans; angle/evaluate public C++ struct methods expose integers (chain.hpp:44-48). Actual callers resolve named bodies with mj_name2id+negative check (`chain.cpp:28-32`, drivetrain.cpp:16-18,60; transmission.cpp:35-38). Python bindings do not expose GeometryWorkspace. Verdict: C++ API hardening opportunity, not currently demonstrated memory-safety bug from valid Python/public config input.

10. **NaN passes chain planar test: literal condition true but outcome qualified.** `chain.cpp:117-120` uses abs(x)>tol so NaN comparison doesn't reject; evaluate chain_geometry then validates finite front/rear/up/reference (`chain.cpp:37-45,153,157-164`), and reference from frame angle becomes nonfinite and is rejected. Corrupt qpos/kinematics can reach public set_state, but no isolated proof evaluate successfully accepts a nonfinite output. Verdict: weak validation style, no independently reproduced successful invalid force result.

11. **angle assumes nq==nv: helper yes, current callers guard.** angle accumulates coordinates vector nv and reads qpos entries0..nv-1 (`chain.cpp:126-131`); evaluate checks nq!=nv at138-140 and accumulated scalar joint topology at141-145. DrivetrainWriter checks at25-27, direct angle caller uses accumulated=false (`drivetrain.cpp:95-97`). Geometric Transmission checks all scalar coordinate coverage and nq==nv (`transmission.cpp:63-67`). Valid MuJoCo ball/free nq>nv, so no qpos over-read anyway, but angular accumulation would be wrong if standalone accumulated angle used. Verdict: current reachable callers safe; helper precondition should be documented.

12. **np_interp empty/mismatched spans: true unchecked helper, unreachable through ProfileQuery.** `profile.cpp:171-173,180,196` dereferences empty/mismatched arrays; public C++ helper declaration `profile.hpp:87-88` doesn't state size contract. Only usage `profile.cpp:461` runs on constructor-checked equal columns of at least2 (`profile.cpp:310-320`), finite query validation at449-451. Not Python-bound. Verdict: hardening opportunity, no current public input reaches the bad helper call.

13. **Heightfield geom_dataid and int overflow: true unchecked trust boundary.** `profile.cpp:222-231` uses geom_dataid as hfield index without bounds; `profile.cpp:233-235` computes signed int start+rows*cols before size_t subspan at238-239. Hfield type/name checked at210-221; valid compiled MuJoCo links a heightfield geom to a real asset. No malformed IDs can be passed via native tire dict. Python oracle also trusts compiled index/raster (`tire_forces.py:25-31`). MuJoCo current nhfielddata is mjtSize while rows/cols are int, so very large otherwise valid allocated rasters are theoretically overflow-prone; not reproduced because huge memory/asset requirement. Controller follow-up: MuJoCo 3.12.0 mj_makeModel limits nhfielddata below INT_MAX; mj_loadModel calls mj_validateReferences, which computes the raster extent in mjtSize and rejects oversized assets. Thus the proposed large valid asset cannot overflow this expression through the present Stepper load path. Local arithmetic remains unsafe for an unvalidated or later-mutated direct C++ model. Corrupted hfield IDs and cyclic parents were saved and independently rejected by Stepper loading in subprocesses.

14. **candidates hi<lo reserve wraps: unreachable valid invariant.** candidates private (`profile.hpp:55-65`), reserve size cast from hi-lo atprofile.cpp:387. Caller contact enforces finite center, positive finite radius, center in domain, strictly increasing px atconstructor337-339; searches at464-465 satisfy c-radius≤c+radius, and lo=max(0,right(left)-2)≤hi=min(count,right(right)+1), including overflow to infinities. Verdict: refute as reachable issue; helper internal precondition.
