**Steps:**

- [ ] `recorder.py`: collect per step and write CSV with Python's standard-library `csv` (pandas is not a dependency and must not become one). Channels: time, X, speed, fork travel and shock stroke (both as shaft mm and as wheel mm), both shaft velocities, spring and damper force separately for each end, bumper force, pitch, per-wheel contact flags and normal loads, wheel power, bar and saddle proper acceleration from the two accelerometers, and the virtual rider's instantaneous moment, accumulated angular impulse and accumulated work.
- [ ] **Carried from Task 3 — the contact-force spikes are still there.** Task 3 capped the load fed to rolling resistance at 3× system weight, but that cap shields only the `Crr·N·r` channel. The underlying normal-load bursts at the square edges are unchanged and reach 11.9 kN front / 16.4 kN rear — 12–16× system weight, in runs of 2–4 timesteps. Any plot or invariant of yours that reads contact or suspension force will see them. Decide deliberately how the plots handle it (they are real solver transients, so clipping them silently would be dishonest; annotating or reporting a percentile alongside the peak is not), and make sure the energy invariant is not dominated by them.
- [ ] `ride_plots.py`: travel versus X with obstacle markers from `TrackSpec.markers`; a **shaft-velocity histogram** for each end (the only view against which HSC/LSC can be tuned sensibly); peak accelerations. Match the existing plot style in `viz/`.
- [ ] `cli/ride.py`: `--track` (preset name, default `enduro_aggressive`), `--speed` (km/h, default 25), `--headless`, `--sag` (target percentage, fits **both ends**), `--out`, `--seed`. Register a `bike-ride` console script in `pyproject.toml`. Artifacts go to `output/ride/<preset>_<speed>/`.
- [ ] `--sag`: call the existing `physics/tuning.py::compute_suspension_tuning_for_sag` with `front_weight_fraction=None` so it fits against the model's own centre of mass, apply the fitted fork pressure and coil rate to the run, and print both. **Do not change the shipped defaults** in `BikeSpecs` — they are documented in the README and pinned by existing tests. At 30/30 against the model CoG the fit is 118.5 psi and 93 984 N/m.
- [ ] `tests/test_ride_telemetry.py`: the CSV has the declared header and one row per recorded step; a short run reproduces bit-identically when repeated with the same inputs; plots render to files without a display.
- [ ] `tests/test_ride_invariants.py`: the invariant suite that replaces a golden telemetry trace — contact with a heightfield is chaotic, so a tolerance-based trace would break on any MuJoCo upgrade. Assert instead: the default run completes without crashing; sag stays within tolerance; suspension travel never exceeds the joint limits **beyond a stated tolerance** — Task 3 measured the shock reaching −0.550 mm past top-out because the ride mode's joint limits are deliberately soft (`solreflimit="0.01 1"`), so the assertion takes a tolerance derived from a measurement you make, not zero and not a number invented to pass; mean speed tracks the target, measured over a window that **excludes the initial ramp** — the bike starts from rest and needs about 8 m to reach the target; total energy does not grow, with the virtual rider's injected work accounted as an explicit source; and **MuJoCo's simulated wheel travel agrees with the analytic solver under riding loads** — the quasi-static baseline is 0.039 mm on wheel travel and 0.014 mm on shaft stroke, so measure the loaded figure and set the tolerance from it, recording the measured value in the test's docstring.
- [ ] **`docs/RIDE.md` contact-debounce note (carried from Task 3).** The ride mode debounces its contact gates: MuJoCo's sphere–heightfield collision drops the contact row for a loaded wheel on a speed-dependent share of steps (measured on flat ground: 2.0 / 14.7 / 27.2 / 43.2 % at 15 / 25 / 35 / 45 km/h), and `sim/ride/contacts.py` holds the last measured load for up to 10 steps (5 ms) so a false airborne does not gate the drive torque off or fire the virtual rider. Record it: a sentence in §6 and §7 where the gates are described, and an entry in §12's list of non-physicalities. State the two facts that make the fixed window sound — the artifact's *duration* is speed-invariant (worst run 1 both-wheel step, 3 single-wheel at 45 km/h) even though its rate is not, and a real both-wheels flight ending inside 5 ms would need a take-off vertical velocity of 0.025 m/s. Note that rolling resistance deliberately consumes the **raw** load rather than the debounced one, because there the artifact costs nothing and the hold would bias a §8 sink.
- [ ] **`docs/RIDE.md` §9 correction (carried from Task 2).** The §9 sag table is wrong and must be fixed. Its figures — 42.0 % front, 25.3 % rear — route the entire axle load through the spring and evaluate at the undeflected centre of mass. Two real effects are missing: the unsprung mass (3.90 kg front = fork lowers + wheel; 5.10 kg rear = chainstay + seatstay + wheel) rests on the contact patch *below* the spring and is never carried by it, and the bike pitches about 1.1° nose-down at sag, redistributing the axle loads. The solved equilibrium gives **40.6 % front / 22.7 % rear**, and feeding the solved contact loads minus unsprung weight back into `ForkAirSpring` and the leverage-ratio solver reproduces it to under 1 mm at both ends. Rewrite the table with two columns — the first-order analytic figure and the solved-equilibrium figure — and state plainly which one the simulation produces and why they differ. Note also that `physics/tuning.py` makes the same first-order simplification in its spring calibration (`f_shock_sag = f_rear_vert * lr_at_sag` uses the full axle load) while correctly subtracting unsprung mass for damping, so the two are consistent with each other and both are first-order. Do **not** change `tuning.py` — recording the discrepancy is this task's job, re-deriving the shipped spring rates is not.
